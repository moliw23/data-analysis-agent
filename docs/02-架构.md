1. `llmProvider.js` 的请求形态已锁定为 OpenAI 兼容：`POST {baseUrl}/v1/chat/completions`，携带 `Authorization: Bearer`，`response_format: {type:'json_object'}`，默认 `temperature: 0.2`，`timeoutMs: 15000`。后端网关必须**逐字节兼容**这个形态，否则前端 4 个钩子全部失效。

3. `src/store.js` 686 行、`src/components/Views.jsx` 706 行，均已超 300 行硬规则。**本次改造不得继续向其追加逻辑**，新能力放进独立模块（见 §7.2）。
4. 现有直连链路是 `browser -> 第三方 LLM` 与 `browser -> db-proxy.mjs -> MySQL/PG`。后端化后，两条链路都应收敛到 `browser -> FastAPI -> 上游`。

## 2. 选型对比矩阵

评分口径：成熟度 / 依赖重量（越轻越好）/ Windows 友好度 / 与 JD 的匹配度。每项 1–5 星。

### 2.1 后端框架（用户已拍板 FastAPI，此处仅确认可行性并锚定版本）

| 候选 | 成熟度 | 依赖重量 | Windows 友好 | JD 匹配 | 结论 |
|---|---|---|---|---|---|
| **FastAPI** | 5 | 4 | 5 | 5 | **选用**。ASGI 原生 async，配合 `httpx` 做 LLM 流式转发无阻塞；自动生成 OpenAPI 3.1 作为前后端契约；与用户已有 `job-tracker` 项目同栈，经验可复用 |
| Flask | 5 | 5 | 5 | 2 | 否决。同步 WSGI，LLM 流式转发需额外引入 gevent/async 适配；无内建 OpenAPI |
| Django + DRF | 5 | 2 | 4 | 3 | 否决。ORM/Admin/迁移全套对单机工具是纯负担，启动体积与心智成本不匹配 MVP |

### 2.2 ORM：SQLAlchemy 2.x vs SQLModel vs 原生 sqlite3

| 候选 | 成熟度 | 依赖重量 | Windows 友好 | JD 匹配 | 结论 |
|---|---|---|---|---|---|
| **SQLAlchemy 2.0.x** | 5 | 4 | 5 | 5 | **选用**。`DeclarativeBase` + `Mapped[]` 类型注解风格是当前主流；与 `job-tracker` 同栈已验证；模型与校验解耦，允许 `schemas/` 的请求/响应模型与表结构**独立演化**（本项目必需：`KbChunk` 表不返回 embedding，`Conversation` 详情返回聚合消息） |
| SQLModel 0.0.47 | 3 | 4 | 5 | 3 | 否决。版本号仍停留在 `0.0.x`，API 未冻结；它强绑定 Pydantic 与 SQLAlchemy 双层约束，当"请求 Schema 与表结构不一致"时反而要写草稿模型绕开，得不偿失 |
| 原生 `sqlite3` + 手写 SQL | 5 | 5 | 5 | 2 | 否决。10+ 张表的 CRUD 手写 SQL 会让 `repositories/` 变成字符串拼接地狱，且失去类型提示。仅作为 embedding 向量兜底存储的备选方案（见 §12 R1） |

### 2.3 向量库三选一（核心选型）

| 候选 | 成熟度 | 依赖重量 | Windows 友好 | JD 匹配 | 结论 |
|---|---|---|---|---|---|
| **ChromaDB 1.5.9（PersistentClient）** | 4 | 2 | **5** | 5 | **选用**。PyPI 实测发布 `chromadb-1.5.9-cp39-abi3-win_amd64.whl`，**预编译轮子，无需 C++ 编译器、无需外部服务**；`chromadb.PersistentClient(path=...)` 进程内嵌持久化；LangChain 生态默认搭配，JD 认知度最高。代价：31 个依赖（含 `onnxruntime`/`grpcio`/`kubernetes`），安装体积约 250–400MB |
| faiss-cpu 1.15.1 + SQLite 存 BLOB | 4 | 4 | 4 | 3 | 备选（不选用）。`faiss_cpu-1.15.1-cp310/cp311-win_amd64.whl` 实测存在，轮子约 30MB，依赖仅 numpy。但它只提供**索引**，元数据/权限/持久化/删除语义全要自研（约 200 行），且换 embedding 维度需全量重建索引文件。对单人 MVP 来说，省下的 300MB 换来的是更多自研代码 |
| pgvector + PostgreSQL | 4 | 1 | **1** | 4 | 否决。Windows 上装 PostgreSQL 服务 + 编译 `vector` 扩展，与"零外部依赖、无 Docker 习惯"的用户画像直接冲突。且该项目是**单机单用户**，引入服务端 RDBMS 无收益 |

**为什么不是"MVP 知识库推荐 pgvector"**：架构知识库 `references/architecture/rag-knowledge-base.md` 的默认推荐是 pgvector + HNSW，其前置假设是"已有 PostgreSQL 业务库"。本项目没有，且用户明确要求零外部依赖纯 pip。**选型必须服从项目约束，不服从模板默认值。**

**ChromaDB 真实 API（已核实官方 cookbook，非推测）**：

```python
import chromadb
client = chromadb.PersistentClient(path=<chroma_dir>)
col = client.get_or_create_collection(
    name=f"kb_{kb_id}",
    embedding_function=None,      # 关键：显式传 None，禁用默认 ONNX 模型，避免自动下载权重
    metadata={"hnsw:space": "cosine"},
)
col.upsert(ids=[...], documents=[...], embeddings=[...], metadatas=[...])
res = col.query(query_embeddings=[...], n_results=k, where={...},
                include=["documents", "metadatas", "distances"])
```

**三条必须写进实现的硬约束**（否则线上必踩）：

1. `embedding_function=None` 必须显式传。不传会触发默认 embedding 模型下载，在无网/慢网环境直接卡死。
2. **collection 名称规则**：长度 3–63，首尾必须是小写字母或数字，中间可含 `.` `-` `_`。本项目用 `kb_{uuid}`（uuid 含连字符，合规）。
3. **Chroma 非进程安全**：官方明确"thread-safe but not process-safe，禁止多进程写同一 path"。这直接决定 `uvicorn workers=1` 与 APScheduler 必须**同进程内运行**（见 §12 R5）。

### 2.4 Embedding 方案

| 候选 | 成熟度 | 依赖重量 | Windows 友好 | JD 匹配 | 结论 |
|---|---|---|---|---|---|
| **OpenAI 兼容 `POST /v1/embeddings`（复用用户已有 baseUrl + apiKey）** | 5 | **5（零新依赖）** | 5 | 4 | **选用**。复用前端已有的 LLM 配置，用户零额外配置；纯 HTTP 调用，不占本地内存与算力 |
| 本地 `sentence-transformers` 6.1.0 | 5 | 1 | 2 | 4 | 否决。硬依赖 PyTorch，Windows CPU 轮子约 2–2.5GB，加上模型权重首次下载。MVP 阶段不应让用户为一个检索功能付出 GB 级下载 |
| 本地 Ollama + `nomic-embed-text` | 4 | 3 | 4 | 3 | 备选（写入 UI 提示，不内建）。需用户自行另装 Ollama 服务，属于"零外部依赖"之外；但作为**隐私完全不出本机**的升级路径值得在文档中告知用户 |

**必须接受的现实风险**：很多"OpenAI 兼容"服务只实现了 `/v1/chat/completions`，**不提供 `/v1/embeddings`**。因此 RAG 检索必须有降级路径 —— 见 §10.2 与 §12 R2。

### 2.5 文档切分

| 候选 | 成熟度 | 依赖重量 | Windows 友好 | JD 匹配 | 结论 |
|---|---|---|---|---|---|
| **langchain-text-splitters 1.1.2** | 5 | 3 | 5 | **5** | **选用**。`RecursiveCharacterTextSplitter` 支持自定义分隔符列表，可传入中文标点 `["\n\n","\n","。","！","？","；","."," ",""]` 解决中文断句；JD 明确提及 LangChain，简历可写。实测依赖仅 `langchain-core<2.0.0,>=1.2.31`，纯 Python |

| LlamaIndex `SentenceSplitter` | 4 | 1 | 4 | 3 | 否决。依赖树比 langchain-core 更重，且引入整套 node/index 抽象，为一个切分函数不划算 |

### 2.6 会话记忆

| 候选 | 成熟度 | 依赖重量 | Windows 友好 | JD 匹配 | 结论 |
|---|---|---|---|---|---|
| **SQLite 表（`conversations` + `messages` + `memories`）+ 滚动摘要** | 5 | **5（复用已有 SQLite）** | 5 | 4 | **选用**。表结构完全可控，可精确实现"上下文窗口预算裁剪 + 超长历史摘要压缩"；查询与列表接口天然贴合前端；零新增依赖 |
| LangGraph checkpoint (`langgraph.checkpoint.sqlite`) | 4 | 2 | 4 | 4 | 否决。引入整个 `langgraph` + `langchain-core` 图执行运行时，为的是用一个 `SqliteSaver` 存消息数组 —— **典型的用框架替代 20 行 SQL**。本项目对话流程是线性四钩子调用，不是有状态的图，LangGraph 的价值（分支/中断/人审）用不上 |
| Redis + TTL 会话 | 4 | 2 | 2 | 3 | 否决。Windows 无原生 Redis，且会话需要长期持久化，TTL 语义相反 |

**长期记忆设计**（不用向量库也能做好）：`memories` 表按 `scope`（global / conversation / dataset）+ `kind`（fact / preference / insight）分类存储；注入上下文时按 `weight DESC, updated_at DESC` 取 Top-N，并对超过 2000 token 的历史消息触发滚动摘要写回 `conversations.summary`。**记忆检索先用 SQL 排序，不建向量索引**——MVP 的记忆条目量级是几十到几百条，语义检索是过度设计。

### 3.3 分层 requirements 策略（控制安装风险）

```
backend/requirements-core.txt   # fastapi uvicorn pydantic pydantic-settings sqlalchemy
                                # apscheduler httpx python-multipart cryptography
backend/requirements-rag.txt    # chromadb langchain-text-splitters pypdf python-docx
backend/requirements-dev.txt    # pytest pytest-asyncio ruff
```

**理由**：`chromadb` 会拉入 `onnxruntime` / `grpcio` / `kubernetes` / `opentelemetry` 共 31 个包。若一并安装在慢网/受限网络下失败，会导致**整个后端装不上**。分层后：核心装完即可启动 LLM 网关 + 会话 + 调度；RAG 装失败时自动降级到 SQLite FTS5 关键词检索（§10.2），项目仍可用。`requirements.txt` 保留为聚合入口，内容为 `-r requirements-core.txt` + `-r requirements-rag.txt`。

## 4. 目标架构

### 4.1 分层与数据流

```
┌──────────────────────────────── 浏览器（React SPA，单端口同源）────────────────────────────────┐
```

## 6. API 端点清单

**统一规则**

- 全部带版本前缀 `/api/v1/`。
- 统一响应信封：
  ```json
  { "code": 0, "data": {}, "message": "" }
  ```
  `code = 0` 表示成功；`code != 0` 时为业务错误码（见 §6.8）。HTTP 状态码同时保持语义（200 / 201 / 400 / 404 / 422 / 500）。
- 分页统一：
  ```json
  { "code": 0, "data": { "items": [], "total": 0, "page": 1, "limit": 20, "hasMore": false } }
  ```
- **认证**列取值：
  - `本机` = 仅监听 `127.0.0.1` + CORS Origin 白名单校验，无登录（单机单用户工具，登录是过度设计）。
  - `本机+确认` = 额外要求请求头 `X-Local-Confirm: true`。用于**写入/覆盖密钥**与**不可逆操作**（清空知识库、重建索引），防 CSRF 与误点。

### 6.1 健康检查与元信息

| Method | Path | 功能 | 认证 | 请求体 | 响应体 |
|---|---|---|---|---|---|
| GET | `/api/v1/health` | 存活 + 各子系统状态 | 本机 | — | `{status, version, subsystems:{db, vector, scheduler, llm_configured}, capabilities:{rag,embeddings,scheduler}}` |

`capabilities` 是**降级策略的开关源**：前端启动时取一次，据此决定 AI 能力面板是否可用、是否显示"关键词降级"提示。必须真实反映后端探测结果，不得硬编码 true。

| GET | `/api/v1/knowledge-bases/{id}/documents/{docId}/chunks` | 分块预览 | 本机 | `?page=&limit=` | 分页信封（含 `seq/content/charLen/meta`） |
| POST | `/api/v1/knowledge-bases/{id}/documents/{docId}/reprocess` | 重新切分 + 重新嵌入 | 本机+确认 | `{chunkSize?, chunkOverlap?}` | `{documentId, status}` |
| POST | `/api/v1/knowledge-bases/{id}/search` | 检索 | 本机 | `{query, mode:'vector'\|'keyword'\|'hybrid', topK?, rerank?, minScore?}` | `{mode:'vector'\|'keyword'\|'hybrid_degraded', items:[{chunkId,documentId,content,score,meta,highlights}], latencyMs}` |
| POST | `/api/v1/knowledge-bases/{id}/reindex` | 重建全库索引（**逻辑重建，不删目录**） | 本机+确认 | — | `{jobId, status:'running'}` |
| POST | `/api/v1/knowledge-bases/{id}/queries/{queryId}/feedback` | 检索效果反馈（知识自演化数据源） | 本机 | `{wasUseful, relevanceScore?}` | `{id}` |

**检索模式语义**：
- `vector`：仅 Chroma 向量检索。
- `keyword`：仅 SQLite FTS5（`tokenize='trigram'`）—— **无 embedding 服务时的可用路径**。
- `hybrid`：向量 Top-50 + FTS5 Top-50，用 RRF（Reciprocal Rank Fusion，`k=60`）融合后返回 Top-K。
- 响应里的 `mode` 字段若为 `hybrid_degraded`，表示请求了 hybrid 但向量侧不可用，已在 FTS5 上完成。**前端必须在 UI 明示降级**，不允许静默。

### 6.8 系统设置与隐私档位（`/api/v1/settings`）

| Method | Path | 功能 | 认证 | 请求体 | 响应体 |
|---|---|---|---|---|---|
| GET | `/api/v1/settings/privacy-mode` | 读取当前档位、实际放行的能力、以及因降级被阻断的既有数据计数 | 本机 | — | `{privacy_mode, effective_grants:{llm_proxy, conversation_persistence, kb_ingest, kb_search, server_sql, external_db_proxy}, blocked_by_downgrade:{server_datasets, knowledge_bases, kb_documents}, updated_at}` |
| PUT | `/api/v1/settings/privacy-mode` | 切换档位（接口层强制生效，不只是前端隐藏） | 本机+确认 | `{privacy_mode:'strict'\|'standard'\|'full'}` | 同 GET |

**为什么需要独立的设置端点**：`privacy_mode` 原本只作为 `/meta/capabilities` 的只读字段存在，但 F0 立为 P0 功能项后它必须是**用户可切换且可被接口验证**的机制。只读字段无法满足验收（"绕过前端直接打接口，确认 strict 下上传被拒"需要先能把档位切到 strict）。

**降级不删除数据**：本机安全策略拦截文件删除，且删用户数据本身也不该是切档位的副作用。`full -> strict` 时既有 `storageMode='server'` 数据集与已入库知识库**保留**，仅后续访问被 `code=4030` 阻断。`blocked_by_downgrade` 如实暴露计数，供 UI 提示"你有 N 个数据集在当前档位下不可用"。这条语义必须在 `PUT` 的响应里就体现，让用户在切档位时立刻知道影响面。

### 6.9 业务错误码

| code | 含义 | HTTP | 触发场景 |
|---|---|---|---|
| 0 | 成功 | 200 / 201 | — |
| 4000 | 参数校验失败 | 422 | Pydantic 校验不通过 |
| 4010 | 缺少本机确认头 | 403 | 需 `X-Local-Confirm: true` 的端点未携带 |
| **4030** | **隐私档位阻断** | **403** | **当前 `privacy_mode` 不允许该操作（详见 §7.4 闸门矩阵）** |
| 4040 | 资源不存在 | 404 | 会话 / 知识库 / 数据集 / 任务 id 不存在 |
| 4090 | 数据集不在服务端 | 409 | `storageMode='local'` 却调 `/query` |
| 4091 | 索引未就绪 | 409 | 知识库仍在 embedding，却发起检索 |
| 4092 | embedding 维度不匹配 | 409 | 换模型后未 reindex 就检索 |
| 4220 | 上游 LLM 失败 | 502 | 全部 provider 均失败（含 fallback 与熔断） |
| 4221 | 上游不支持 embeddings | 502 | provider 无 `/v1/embeddings`（前端应切关键词模式） |
| 4222 | LLM 未配置 | 400 | 无可用 provider |
| 4290 | 速率 / 并发超限 | 429 | 嵌入任务并发超过 `limits.MAX_EMBED_CONCURRENCY` |
| 5000 | 内部错误 | 500 | 未捕获异常（日志记 stack，响应不泄漏细节） |

**4030 与 4010 的区别**（前端错误处理不要混）：`4010` 是"你忘了带确认头"，前端补上头重试即可；`4030` 是"当前档位不允许，补头也没用"，前端必须引导用户去设置页切档位，**禁止自动重试**。

### 7.4 privacy_mode 闸门矩阵与实现位置

> F0 已立为 P0 横切功能项，验收要求「绕过前端直接打接口，确认 strict 下上传被拒」。本节给出闸门的完整落点与实现结构，回答"是否只靠一个 FastAPI dependency 就能统一覆盖"。

#### 7.4.1 闸门矩阵（逐端点的档位判定）

| 端点 | strict | standard | full | 判定依据 |
|---|---|---|---|---|
| `POST /llm/chat`、`/llm/chat/stream` | 放行 | 放行 | 放行 | LLM 代理是 strict 的核心保留能力 |
| `POST /llm/embeddings` | 放行 | 放行 | 放行 | 工具型能力；是否被业务使用由上层闸门决定 |
| `GET/POST /llm/providers`、`/llm/routes`、`/llm/usage`、`/llm/logs` | 放行 | 放行 | 放行 | 密钥托管与记账，属"可审计"而非"外传内容" |
| `POST /conversations`、`/messages`、`/memories` | 放行 | 放行 | 放行 | 会话内容注定要发给模型，未新增外传面 |
| `GET /conversations/{id}/context`、`/summarize` | 放行 | 放行 | 放行 | 同上 |
| `POST /knowledge-bases`（建库） | **阻断 4030** | 放行 | 放行 | 建库即声明要入库内容，与上传同档位 |
| `POST /knowledge-bases/{id}/documents`（上传） | **阻断 4030** | 放行 | 放行 | 主要闸门；文件落 `data/uploads/` 且分块入 Chroma |

| `POST /knowledge-bases/{id}/reindex` | **阻断 4030** | 放行 | 放行 | 全库重新嵌入 |
| `POST /knowledge-bases/{id}/search` | **阻断 4030** | 放行 | 放行 | **检索会把命中分块送入 prompt**，属外传用户内容，故与入库同档位 |
| `POST /datasets`（`storageMode=local`） | 放行 | 放行 | 放行 | 只登记 schema，无明细，与既有产品行为一致 |
| `POST /datasets`（`storageMode=server`） | **阻断 4030** | **阻断 4030** | 放行 | **请求体级闸门**，见 §7.4.2 第 ① 类 |

| `POST /datasets/{id}/query`（服务端 SQL） | **阻断 4030** | **阻断 4030** | 放行 | 同上；注意与 4090 区分：4090 是"数据集本身没上服务端" |

#### 7.4.2 一个 dependency 不够 —— 需要「一个策略对象、三类消费点」

**结论：单靠 `Depends(...)` 无法统一覆盖。** 原因是有三类判定，它们在请求生命周期中的位置不同：

| 类型 | 说明 | 为什么 dependency 覆盖不了 | 落点 |
|---|---|---|---|
| ① **路由级闸门** | 整个端点在该档位下禁用（如上传、reindex） | 可以覆盖。这类**确实**用一个 dependency 工厂就能统一 | `api/deps.py::require_privacy(*allowed)` 挂在路由 `dependencies=[...]` |
| ② **请求体级闸门** | 同一端点因 body 字段值不同而判定不同（`POST /datasets` 的 `storageMode`；`POST /schedules` 引用的资源） | dependency 在路由声明处执行，**无法按 body 字段有条件放行**。必须下沉到 Pydantic `model_validator` 或 service | `schemas/dataset.py` 校验 + `services/dataset_service.py` 二次校验 |
| ③ **能力声明派生** | `GET /meta/capabilities` 的 `rag` / `server_sql` 必须与闸门判断**同源** | dependency 不管响应体。若两处各写一份判断逻辑，必然漂移（表现为：UI 显示可用但接口返回 4030，或反之） | `routes/health.py` 读同一策略对象 |

**统一机制**：`core/privacy.py` 定义单一 `PrivacyPolicy` 值对象，提供 `allows_kb_ingest()` / `allows_kb_search()` / `allows_server_sql()` / `allows_external_db()`，上述三类消费点全部读它。

```
core/privacy.py
  PrivacyPolicy(privacy_mode)                     # 唯一判定真相源
    ├─ allows_kb_ingest()      -> mode in (standard, full)
    ├─ allows_kb_search()      -> mode in (standard, full)
    ├─ allows_server_sql()     -> mode == full
    ├─ allows_external_db()    -> True（显式裁定，见 §7.4.1）
    ├─ derive_capabilities(probe) -> Capabilities   # 与闸门同源的能力声明
    └─ blocked_counts(db)      -> {server_datasets, knowledge_bases, kb_documents}

消费点：
  api/deps.py::require_privacy(*allowed)  ── 路由级（① 类，约 6 处）
  schemas/*.py + services/*.py            ── 请求体级（② 类，约 2 处）
  api/routes/health.py                    ── capabilities 派生（③ 类，1 处）
```

**依赖方向的约束**：`core/privacy.py` 只依赖 `core/config.py` 的档位值，**不得** import `models/` 或 `services/`（`blocked_counts` 通过参数注入 db session 或由 service 计算后传入）。否则 `core/` 会反向依赖上层，违反 §4.2 依赖方向。

#### 7.4.3 闸门的四个工程要求

1. **闸门在 service 层也校验一次**（不只靠 dependency）。原因：调度任务是从 APScheduler 后台线程进入的，**不经过 HTTP 路由**，路由级 dependency 对它完全无效。`schedule_service` 执行任务前必须自己读一次策略。这是最容易漏的一处。**"绕过前端的入口"其实有两个：前端直连接口，以及自家调度线程。**验收要同时覆盖这两条路径。
2. **`capabilities` 与闸门必须同源**（§7.4.2 ③）。测试要覆盖"UI 可见性 == 接口可调用性"的一致性：对每个档位，遍历受闸门管控的端点，断言 `capabilities` 的声明与接口实际返回一致。
3. **4030 响应必须带可执行指引**，而不只是拒绝（结构见 §7.4.4）。前端据此渲染"去设置页切换"的引导，而不是显示一个裸错误。
4. **闸门是贯穿式交付，不是某一期的结尾工作**。见 §13 的分期说明。

#### 7.4.4 code=4030 响应体（8 个受控端点共用同一形状）

契约定义见 `docs/api/openapi.yaml` 的 `components/schemas/PrivacyBlockedData` 与 `components/responses/PrivacyBlocked`（单一定义，非逐端点复制）。

```json
{
  "code": 4030,
  "data": {
    "current_mode": "strict",
    "required_modes": ["standard", "full"],
    "capability": "kb_ingest",
    "setting_path": "/api/v1/settings/privacy-mode",
    "blocked_by_downgrade": { "server_datasets": 0, "knowledge_bases": 0, "kb_documents": 0 }
  },
  "message": "当前隐私档位为 strict，知识库入库已停用。切换到 standard 或 full 档后可继续。"
}
```

| 字段 | 类型 | 语义 | 前端为什么需要它 |
|---|---|---|---|
| `current_mode` | `'strict'\|'standard'\|'full'` | 当前生效档位 | 渲染"当前为 X 档" |
| `required_modes` | 数组 | **可放行该操作的全部档位集合**（非仅最小档位） | 直接渲染"需要 standard 或 full 档"，且前端**不必知道档位的偏序关系** |
| `capability` | `'kb_ingest'` \| `'kb_search'` \| `'server_dataset_register'` \| `'server_sql'` | 机器可读的能力键 | 用于选文案模板，**避免前端硬编码"端点 -> 文案"映射表** |
| `setting_path` | 字符串 | 切换档位的端点路径 | 生成跳转链接，不硬编码路由 |
| `blocked_by_downgrade` | 对象（三计数） | 因当前档位不可访问的既有数据量 | 渲染"你有 N 个数据集、M 个知识库（共 K 份文档）在当前档位下不可用"。**字段恒存在，无被阻断数据时为 0**，前端免去 undefined 判断 |

**能力键与端点的对应**（4 键覆盖 8 个受控端点，多个端点可共享一键）：

| capability | 覆盖端点 |
|---|---|
| `kb_ingest` | 建库、文档上传、重新切分与嵌入、重建索引 |
| `kb_search` | 知识库检索 |
| `server_dataset_register` | 数据集以 `storageMode=server` 注册（**请求体级闸门**） |
| `server_sql` | 数据集明细上传、服务端 SQL 查询 |

**这个载荷由 `PrivacyPolicy` 直接生成**，与闸门判定、`capabilities` 派生共用同一对象 —— 所以三者不可能漂移。这正是 §7.4.2「一个策略对象、三类消费点」的直接收益，也是不把闸门判断散落各处的理由。

#### 7.4.5 闸门映射的唯一真相源在代码里，不在文档里

上面 §7.4.1（18 行矩阵）与 §7.4.4（4 行 capability 映射表）是**人读的说明性视图，不是真相源**。真相源是 `core/privacy.py` 中的一个模块级常量：

```python
# core/privacy.py
CAPABILITY_GATES = {
    "kb_ingest":                ("standard", "full"),
    "kb_search":                ("standard", "full"),
    "server_dataset_register":  ("full",),
    "server_sql":               ("full",),
}
```

`PrivacyPolicy` 的全部方法、`derive_capabilities()`、4030 载荷的 `required_modes` 字段**都由这个常量派生**，不各自硬编码档位元组。

**测试怎么拿到矩阵（重要，避免造第三份副本）**：

| 做法 | 评价 |
|---|---|
| 测试 `from app.core.privacy import CAPABILITY_GATES` 直接导入，遍历断言 | **推荐**。零副本，改了常量测试立刻跟上 |
| 把矩阵导出成 `tests/data/*.json` 供测试读 | 可接受但劣于上者 —— 它是第二份副本，需要人工同步 |
| 把 §7.4.1 的 18 行矩阵抄进 PRD 或测试文件 | **禁止**。这正是 `capabilities` 漂移的同构版本 |

**推论（对 §5.1 硬规则的补充）**：任何"端点 → 允许档位"的映射只允许出现在 `CAPABILITY_GATES` 一处；`api/deps.py` 的 `require_privacy(*allowed)` 调用处**必须传 capability 键**并内部查表，不得写成 `require_privacy("standard", "full")` 这类字面量。这样档位集合变更只需改一行常量，且 `grep -rn '"standard", "full"' app/` 只应命中 `core/privacy.py`。

> 这条与 §7.4.2「一个策略对象、三类消费点」是同一思路的延伸：**漂移风险不只在"PRD 与架构之间"，也在"同一个契约的内部重复"与"文档与代码之间"。** 判定的唯一真相源始终是代码，文档只做说明。

### 7.5 "出本机"凭据：`ingested_mode` 是授权凭据，`egress_at` 才是事实凭据

> 需求来源：PRD §6.1 验收⑥ + §11 指标「出本机内容自查可达率 100%」。承诺 3 说 RAG 是"唯一默认出本机通道、由用户主动发起且 UI 明示"—— 那么"我到底哪些内容出过本机"是这条承诺的必要配套，**没有事后可查，承诺 3 只有事前告知、缺了一半**。

#### 7.5.1 两个字段语义不同，不能互相替代

| 字段 | 语义 | 回答的问题 | 能否用于筛选 |
|---|---|---|---|
| `ingested_mode` | 最近一次入库时所处的档位（枚举仅 `standard` / `full`） | **谁授权**了这次入库 | **不能**（见 §7.5.2） |
| `ingested_at` | 最近一次入库时间（含 reprocess / reindex） | 何时入库 | 不能 |
| `egress_at` | 内容**实际**离开本机的时间；NULL = 从未离开 | **有没有真的出去** | **能 —— 这是筛选器的唯一判定依据** |
| `egress_channel` | 首次外传的通道（`embedding` / `retrieval` / `both`） | 为什么会出去 | 辅助说明 |
| `embedding_sent` | 分块文本是否**曾经**被发往上游 embedding 接口 | 向量化是否真的外传了 | 不能（会漏掉 retrieval 通道） |

**`ingested_mode` 为什么不包含 `strict`**：`strict` 档下入库能力已被闸门阻断（§7.4.1），系统内不可能存在 strict 入库的文档。这是一条可断言的不变量，测试应覆盖。

#### 7.5.2 筛选器谓词必须是 `egress_at IS NOT NULL`，不能是 `ingested_mode`

这是本设计最容易做错、且**做错了会给出假答案**的一处，踩的正是 PM 那条线：「标注错了比不标注更危险」。

**反例（真实且高概率）**：provider 不支持 `/v1/embeddings` 时（§12 R2，概率标为**高**），入库会降级为 FTS5 关键词模式，**分块文本从未发往上游**。此时：

- `ingested_mode = 'standard'`（因为入库确实在 standard 档下发生了）
- 但内容**没有**离开本机

若筛选器用 `ingested_mode` 判定，**整个知识库的每一份文档都会被标成"已出本机"** —— 不是个别误标，是全库系统性误报，且误报方向会让用户高估自己的暴露面。这种"永远为真"的筛选器等于没有筛选器，但用户会以为它在工作。**这比不提供筛选入口更坏。**

**必然后果**：`egress_at` 不是可选优化，它是让验收⑥真正成立的前提。PM 要求的两个字段（`ingested_mode` / `ingested_at`）是必要的授权凭据，但**不足以**支撑筛选器。

#### 7.5.3 `egress_at` 的两个实现约束

1. **一经置位永不复位（sticky）**。数据无法撤回 —— 内容已经发到上游了，之后用户切回 `strict` 也不会让它回来。任何"按当前档位重算"的实现都是错的。这条同样适用于 `embedding_sent`、`egress_channel`（`egress_channel` 允许 `embedding` -> `both` 的升级，但不允许回退）。
2. **两个置位时机都必须覆盖**：
   - **入库时**：`embedding_service` 成功调用了上游 embedding 接口 → `egress_channel='embedding'`。
   - **检索注入时**：检索结果中的分块被放进发往上游 chat 的 prompt（如绑定知识库的会话）→ 若此前为 NULL 则 `egress_channel='retrieval'`，若已是 `embedding` 则升为 `both`。
   **只覆盖第一个会漏报检索通道** —— 而检索注入恰恰是 `standard` 档下内容外传的主路径。

#### 7.5.4 范围澄清：本地服务落盘 ≠ 出本机

"出本机"专指**发往上游 LLM / embedding 服务**。以下都不算，不得进入筛选器：

| 动作 | 是否出本机 | 理由 |
|---|---|---|
| 数据集明细上传到本地 FastAPI（`full` 档） | **否** | 落在 `127.0.0.1` 的 SQLite，目标是本机 |
| 服务端执行只读 SQL | **否** | 同上，结果回浏览器 |
| 文档原文件存 `data/uploads/` | **否** | 落本机磁盘 |
| 分块发往上游 `/v1/embeddings` | **是** | `egress_channel=embedding` |
| 分块进入 prompt 发往上游 chat | **是** | `egress_channel=retrieval` |
| schema / 统计摘要发往上游 chat | **是**（既有行为，非本次新增） | 数据集侧的外传通道，与知识库筛选器分开统计 |

**推论**：`datasets` 表**不需要** `egress_at` 字段 —— 它的外传路径（schema / 统计摘要进 prompt）在改造前就存在，且不涉及"用户主动上传内容"这一承诺，不属承诺 3 的覆盖范围。若未来要为用户提供"全量外传自查"，那是独立需求，应收敛到 `llm_call_logs` 而非在每张业务表加字段。

### 8.4 关键取数口径（写进 repository，防止各处口径不一）

- **Token 用量**：`SUM(prompt_tokens)` / `SUM(completion_tokens)` 仅统计 `status='ok'` 且有 usage 的记录；上游未返回 usage 时该行两个字段为 NULL 而非 0（NULL 表示"未知"，0 表示"确实为 0"，语义必须区分）。

## 9. 三层检索漏斗（RAG 实现细节）

```
用户查询
   │
   ├─[第 1 层 向量召回]  Chroma query(query_embeddings, n_results=50, where={doc status: ready})
   │                     依赖：embedding 可用 && index_status='ready'
   │                     不可用 -> 该层返回空，mode 标记为降级
   │
   ├─[第 2 层 关键词召回] SQLite FTS5: SELECT rowid, bm25(kb_chunk_fts)
   │                     FROM kb_chunk_fts WHERE content MATCH ? AND kb_id=?
   │                     ORDER BY bm25(kb_chunk_fts) LIMIT 50
   │                     作用：① 语义失效时的独立召回路径 ② 精确数字/术语的兜底
   │
   ├─[第 3 层 融合排序]  RRF: score(d) = Σ 1/(k + rank_i(d)),  k=60
   │                     两路都命中 -> 加权靠前（天然去重与交叉验证）
   │
   └─[过滤]  文档状态过滤（仅 ready）-> 最低分阈值 minScore -> 未来可加数据集/时间过滤
             │
             ▼
         Top-K（默认 5，上限 20）
```

**分块策略（`chunking_service.py`）**：

1. 先用 `RecursiveCharacterTextSplitter`，分隔符序列针对中文定制：
   `["\n\n", "\n", "。", "！", "？", "；", "，", ".", " ", ""]`
2. `chunk_size=800`（字符，非 token），`chunk_overlap=120`。中文 1 字符约 1–1.5 token，800 字符约 1000 token，配合 Top-5 注入约 5000 token，是安全预算。
3. 每个 chunk 保留元数据：`{doc_id, doc_name, seq, page, section, char_len}`，写入 `kb_chunks.meta_json` 与 Chroma `metadatas`，用于前端引用溯源（"该结论来自 文档名 第 3 页"）。
4. 超长段落（> 2000 字符且无标点，如日志/JSON 行）再套一层字符滑窗，保证不产生超大块。

**嵌入批处理**：`embedding_service.py` 按批（默认 32 条/批）调用 `/v1/embeddings`，批间用 `asyncio.Semaphore(limits.MAX_EMBED_CONCURRENCY)` 限流，失败批次指数退避重试 2 次后标文档 `status='failed'` 并写 `error`，**不阻塞其他文档**。

## 10. 降级策略（后端不可用 / 能力缺失）

### 10.1 后端完全不可用

**探测**：前端启动时调 `GET /api/v1/health`，超时 1.5s；结果缓存 30s；失败时进入 `backendMode = 'offline'`。

| 能力 | 后端在线 | 后端离线（降级行为） | 用户可见提示 |
|---|---|---|---|
| 图表规划 / 结论叙述 / 意图解析 / Text-to-SQL | 走 `/llm/chat` | 回退到 `llmProvider.js` 原有 localStorage 直连（代码保留不动） | 顶部状态条：「本地服务未启动，已切回浏览器直连模式」 |
| LLM Key 存储 | 后端 Fernet 加密落库 | 回退 localStorage（原 `data-agent.llm.config`） | 设置页标注「当前密钥存于浏览器 localStorage，存在 XSS 风险」 |
| 多轮会话 | 后端持久化 | 回退现有的 `store.chat` 内存数组（刷新即失） | 对话面板标注「会话未持久化」 |
| 长期记忆 | 后端 | 不可用 | 记忆面板置灰，附启动指引 |
| RAG 知识库 | 后端 | 不可用 | 知识库入口显示「需启动本地服务」，附一键启动命令 |
| 调度执行与推送 | 后端 APScheduler | 回退到 `src/schedule.js` 现有演示级实现（`setInterval`，仅页面打开时生效） | 调度页标注「当前为演示模式，关闭页面即停止」 |
| 数据集 / 分析 / 清洗 / 图表 / 报告导出 | 不受影响 | 不受影响 | 无提示（这些本来就在本地） |

**核心承诺**：后端离线时，**原有 9 个视图与全部本地分析能力必须 100% 可用**。这是硬验收项，Phase 4 测试要专门覆盖"杀掉后端进程后前端功能完整性"。

### 10.2 后端在线但能力缺失

| 缺失项 | 探测方式 | 降级 |
|---|---|---|
| 未配置任何 provider | `/meta/capabilities.llm_configured=false` | 4 个钩子直接走既有 mock 路径（`withLLMFallback`），AI 面板显示「未配置模型服务」引导 |
| provider 无 `/v1/embeddings` | `/llm/providers/{id}/test` 探针结果落 `embedding_probes` 表 | RAG 检索自动切 `keyword`（FTS5）模式；建库时直接警告「本 provider 不支持语义检索，将使用关键词检索」 |
| 向量索引未就绪 | `index_status != 'ready'` | 检索返回 `code=4091` + `progress`；前端显示入库进度 |
| embedding 模型变更未 reindex | `knowledge_bases.needs_reindex=true` | 检索返回 `code=4092`；前端提供「重建索引」按钮 |
| chromadb 未安装（RAG 依赖装失败） | `/meta/capabilities.rag=false` | 知识库入口隐藏；`requirements-rag.txt` 安装指引显示在设置页 |
| Chroma 目录损坏 | `vector_repo` 初始化异常被捕获 | 记录日志，`capabilities.rag=false`，**不删除目录**（环境约束），提示用户手工改名 `chroma` 目录后重建 |

**降级铁律**：**禁止静默降级**。任何降级都要在响应体与 UI 上可见（响应里的 `mode` 字段 + 前端状态条/徽标）。原因：数据分析场景下"以为在用语义检索、实际在用关键词"会直接导致用户对结论可信度误判。

## 11. 部署方案

### 11.1 生产：单端口（推荐）

```
用户浏览器  →  http://127.0.0.1:8000
                     │
        FastAPI（uvicorn workers=1）
          ├─ /api/v1/*      → 业务路由（先注册）
          ├─ /docs /openapi.json → FastAPI 自生成契约（先注册）
          ├─ /assets/*      → StaticFiles 托管 dist/assets（带 hash，长缓存）
          └─ 其他路径        → 404 兜底返回 dist/index.html（Cache-Control: no-cache）
```

**注册顺序是硬约束**：所有 `/api/v1/*` 路由与 `/docs` 必须在 `app.mount("/", StaticFiles(...))` **之前**注册，否则会被静态资源通配挂载吞掉（`job-tracker` 的 `main.py` 注释已记录此坑）。

**SPA fallback 实现（`core/errors.py`）**：

```python
@app.exception_handler(StarletteHTTPException)
async def spa_fallback(request: Request, exc: StarletteHTTPException):
    path = request.url.path
    if exc.status_code == 404 and not path.startswith(("/api/", "/docs", "/openapi.json", "/redoc")):
        index = Path(settings.frontend_dist) / "index.html"
        if index.is_file():
            return FileResponse(index, headers={"Cache-Control": "no-cache"})
    return JSONResponse(
        {"code": exc.status_code * 10, "data": None, "message": str(exc.detail)},
        status_code=exc.status_code,
    )
```

**缓存策略**（发版必踩的坑）：`index.html` 必须 `no-cache`，`/assets/*`（Vite 带内容 hash）设 `Cache-Control: public, max-age=31536000, immutable`。否则用户升级后会加载到引用已删除 chunk 的旧 `index.html`，白屏。

**启动**：

```bash
cd backend
python run.py            # 默认 127.0.0.1:8000
```

`run.py` 固定 `workers=1`（APScheduler 与 Chroma 都是单进程约束，见 §12 R5），`reload` 由环境变量 `DA_RELOAD=1` 控制，默认关闭。

**构建前端**：

```bash
npm run build            # 产出 dist/，后端自动识别并托管
```

### 11.2 开发：双端口

| 端口 | 服务 | 说明 |
|---|---|---|
| 5173 | Vite dev server | 前端热更新 |
| 8000 | uvicorn（`DA_RELOAD=1`） | 后端热重载 |

`vite.config.js` 增加：

```js
server: {
  host: true,
  port: 5173,
  proxy: {
    '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true },
  },

```

同源代理后，前端 `src/backend/client.js` 的 baseURL 直接写空字符串（相对路径 `/api/v1`），**开发与生产零差异**，不需要 `VITE_API_BASE` 之类环境变量。这是刻意的简化：少一个环境变量就少一类"本地能跑线上挂"的故障。

后端 CORS 白名单（仅开发需要）：`http://localhost:5173`、`http://127.0.0.1:5173`、`http://127.0.0.1:8000`。生产同源，CORS 实际不生效但保留配置无害。

### 11.3 环境约束：禁止删除步骤（硬约束）

本机安全策略拦截任何文件删除操作，回收站 COM 不可用。因此：

| 场景 | 常规做法（禁止） | 本项目做法（合规） |
|---|---|---|
| 重建知识库索引 | 删除 `data/chroma/` 目录后重建 | 调 Chroma API `client.delete_collection(name)` + 重建 collection（**纯 API 调用，不碰文件系统**）；`kb_documents` 置 `deleted_at` 软删 |
| 删除文档 / 数据集 | 删物理文件 | 软删 `deleted_at`；原文件保留在 `data/uploads/` |
| 日志轮转 | 删除旧日志 | 改名为 `app.log.1`、`app.log.2`（保留最近 3 份，**不做删除**） |
| 删除 Chroma 目录内容 | `shutil.rmtree` | 不实现该功能。若目录损坏，在文档中指导用户**手工改名**目录 |
| 数据库重置 | 删除 `app.db` | 不提供重置接口。改为在 `data/` 下新建带时间戳的新库并切换 `DA_DB_PATH` |
| 部署脚本 | `npm run clean` / `rimraf dist` | **部署脚本中不得出现 `rm` / `rmdir` / `rimraf` / `shutil.rmtree` / `Remove-Item`**；构建直接覆盖写入（Vite 默认覆盖 `dist/`，已验证可行） |
| 测试覆盖率目录 | Vitest `coverage.clean: true` | 保持现有 `clean: false`（`vite.config.js` 已注释说明此原因，不要改回去） |

> 该约束是**部署脚本的验收项**：Phase 4 交付的启动/构建脚本里出现任何删除命令即视为不合格。

### 11.4 门禁脚本 `scripts/check_contract.py` 的职责边界

门禁本身也需要边界，否则会以两种方式失效 —— **空转**（断言恒真）与**误报**（断言范围过宽）。两者最终都导致门禁被忽略，与没有门禁等效。

**已消除的空转点**（一度真实存在）：

| 断言 | 原实现的空转方式 | 现实现 |
|---|---|---|
| `$ref` 完整性 | 用正则 `\$ref: '...'` 从文本抠，**只匹配单引号**；改成双引号就匹配到空集、静默通过 | 走**解析后的文档树**收集（`_iter_refs`），对引号风格/缩进/流式写法免疫；并断言"解析数非空"，解析为空即报错 |
| 硬编码颜色 | 正则只认 `#xxxxxx`；**裸 `rgba()` / `rgb()` / `hsl()` 是盲区** —— 而本项目实际存在 9 处裸 rgba | 同时匹配 hex 与 `rgb|rgba|hsl|hsla(`，已用 6 个正负用例验证 |
| 架构文档结构 | 无校验；实际发生过"插入新小节时吞掉 `## 8.` 标题" | 6 个承重小节标题断言存在，已做正负向验证 |

> **断言"解析结果非空"不属于计数口径。** 计数口径的问题是"应有 N 处"随代码增删失真；而"解析到 0 个 $ref / 0 个文档"不是合法的业务状态，它是**校验器自己坏了**的信号。两者性质不同，前者该禁，后者该留。

**刻意排除的范围（防误报）**：颜色与 emoji 扫描**只覆盖架构侧自有产出物**（`docs/02-架构.md`、`docs/decisions/ADR-001-backend-stack.md`）与契约文件，**不扫描全部 `docs/**`**。理由：

- `docs/03-UIUX-附录A-Token清单.md` 是颜色的**唯一真相源**，它必须列出色值 —— 扫描它必然假失败。
- `docs/01-PRD.md` 会引用违规色值作为**缺陷描述**（"清除第二套语义色板的那三处")—— 扫描它同样假失败。
  本文件同理**不转述**那几个色值：转述等于给同一组颜色再造一个存放处，属 §7.4.5 禁止的重复；需要具体值请查设计师的 Token 清单。
- 代码侧的硬编码颜色属前端 lint 门禁职责，不在本脚本范围。

> 实测教训：把扫描范围从 3 份文件放宽到 `docs/**`（9 份）后，门禁立刻报出 6 处"违规"，其中绝大多数是**设计文档合法引用色值**。若不收窄，团队会开始忽略这个门禁 —— **一个会误报的门禁比没有门禁更糟，因为它消耗的是对整套门禁的信任。**

**分层职责**：本脚本管"契约与架构文档的一致性与合规"；代码规范（300 行上限、无硬编码颜色、无 emoji 图标）由前后端各自的 lint/门禁负责。两者不重叠、不互相替代。

## 附：隐私卖点的正面回答

**问题**：加了后端之后，原始的"原始数据不出本机"还剩多少？

**回答**（分三层，不含糊）：

1. **明细数据仍然不出本机，这一条没有让步。** 默认 `storageMode='local'`，原始行数据只存在于浏览器 IndexedDB 与内存。后端只拿到 schema（列名、类型、语义角色）、行数、sha256。这不只是承诺，而是**架构上的强制**：后端根本没有接收明细的接口，除非用户对某个数据集显式执行"上传到本地服务"，且该接口需要 `X-Local-Confirm` 二次确认。

2. **AI 能力的数据去向没有变得更差，反而变得更可审计。** 改造前：浏览器把 schema 与统计摘要经 HTTPS 直接发给第三方 LLM。改造后：浏览器发给本机 127.0.0.1 的 FastAPI，FastAPI 再转发给同一家第三方 LLM。**数据最终到达的第三方没有变化**。变化的是：① 密钥不再落在浏览器（消除 XSS 窃取路径）② 每一次调用都有日志、token、耗时记录，用户可以自己查"到底发出去了什么、发出去了多少" ③ 多 provider 路由让用户可以随时把 baseURL 切成本机 Ollama，此时数据**真正完全不出本机**。

3. **新增的 RAG 知识库是唯一"默认出本机"的通道，而它由用户主动发起。** 用户选择上传文档到本地知识库时，文档的分块文本会进入检索上下文并随 prompt 发给上游 LLM。这一点必须在 UI 上传前明确告知，不能藏在文档里。

**诚实的结论**：卖点从「数据不出本机」精确化为「**分析明细不出本机 · AI 调用可断可审可换本地模型 · 出本机仅限用户显式上传的知识库**」。这个表述比原来弱，但它是真的。原有的绝对化卖点在有 LLM 参与的那一刻就已经不成立了（LLM 调用本身就是出本机），引入后端并没有让它更糟，而是让它从"不可审计的隐含事实"变成"可配置、可审计、可选本地"的显式设计。

同时提供 `privacy_mode` 三档（读写端点见 `GET/PUT /api/v1/settings/privacy-mode`，闸门矩阵见 §7.4.1）让用户自己决定边界。三档语义已收敛为一句可解释的话：**`strict` = 不出本机的功能全关**。

- `strict`（默认）：知识库入库**与检索**、数据集上云全部停用；后端只做 LLM 代理 + 会话元数据。检索一并阻断的理由：只断上传不断检索，等于 `standard` 期间入库的文档在降级后继续随 prompt 外传，档位形同虚设。
- `standard`：额外允许知识库（建库、上传、重建索引、检索）。
- `full`：额外允许数据集明细上传到服务端并执行只读 SQL。

**降级（`full`/`standard` -> `strict`）不删除任何既有数据**，仅阻断后续访问，并由 `blocked_by_downgrade` 计数如实告知影响面（§7.4.4）。这条不只是为了迁就本机"禁止删除"的环境约束 —— 更关键的是**信任**：若用户调回 `strict` 就发现数据没了，他下次不敢再往上调档，档位机制会退化成"永远停在 strict"，F0 就白做了。

**一处显式裁定而非遗漏**：`POST /api/v1/db-proxy/query` 在**三档下均放行**。其目标是用户自指定的数据库，凭证与结果均不落服务端，属"用户自己的数据出口"而非"我们的存储"。验收矩阵中该格"应放行"，不算漏测（§7.4.1）。
