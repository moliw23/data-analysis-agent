## 0. 勘误声明（优先阅读）

我在 Phase 1 首轮汇报中给出过「**72 处硬编码色值**」这个数字。经本轮逐行清点，**该数字口径有误**，此处更正：

| 口径 | 数量 | 说明 |
|---|---|---|
| 颜色字面量总数（hex + rgba） | **119 处** | 72 hex + 47 rgba，含所有类别 |
| 其中：旧令牌定义块（**整块删除，非迁移**） | **32 处** | `styles.css` L2–15 与 L694–707，共 26 hex + 6 rgba |
| 其中：白/黑例外（**按规范保留**） | **15 处** | `#fff` ×10、`#ffffff` ×3、`rgba(255,255,255,…)` ×2；另 2 处同时属旧令牌定义（L5 / L7） |
| 其中：破损声明（**改写为令牌引用**） | **20 处** | 即缺陷清单第 1 项，分布在 17 行 |
| **其中：需逐条迁移到令牌** | **54 处** | **35 hex + 19 rgba** ← 这才是真正的"硬编码违规"数 |

**为什么必须更正**：把 26 处旧令牌定义和 15 处白/黑例外算进"硬编码违规"，会让 F3 的核对者去找 72 个迁移点却只找到 54 个，误判为"漏改 18 处"。**口径必须唯一。** 本附录的 §3 迁移映射表覆盖全部 54 处，可逐条打勾。

### 0.1 本轮二次更正：54 处已不是验收标准（PM 裁定）

> **重要**：PM 已据此把 F3 的验收口径从「**已迁移 54 处**」改成「**不存在未迁移的硬编码颜色**」这个**不变量**。

原因正是上面那个错误本身证明的：**计数型验收会随代码变化而失效** —— 明天有人新增一处彩色，"迁移了 54 处"仍然为真，但已经违规了；而按 72 核对又会误判漏改 18 处。

因此：

| 本文件中的数字 | 现在的性质 |
|---|---|
| §0 的 119 / 32 / 15 / 20 / 54 | **参考信息**。用于说明缺口规模与口径拆分，**不作为验收标准** |
| §2 / §3 的"54 处" | **工作清单**。前端照着改就有 54 个动作，改完即达标 |
| §4.3 的 6 条不变量 | **验收标准**。跑 §4.1 的脚本，全部输出为空即通过 |

**读法**：§3 是"怎么改"（照单做事），§4.3 是"改完没"（照脚本判定）。**不要把 §3 的条数当成 §4.3 的判定依据。**

## 1. 令牌的四层架构总览

参照 152+ 设计系统的 Token 管理标准，本项目令牌按四层组织。`design-tokens.json` 顶层共 **18 个域**。

```
C-extension（品牌专属）
    └── B-slot（≥1 品牌别名槽位）
            └── A2（有默认值）
                    └── A1-identity / A1-structure（品牌核心，不可省略）
```

| 层 | 谁决定值 | 省略后果 | 本项目实例 |
|---|---|---|---|
| **A1-identity** | 品牌方 | 门禁检查失败 | `--bg` `--fg` `--accent` `--font-display` |
| **A1-structure** | 品牌方 | 门禁检查失败 | `--text-*` `--space-*` `--radius-*` `--container-max` `--z-*` `--bp-*` |
| **A2** | 品牌方（有默认值） | 门禁检查失败 | `--motion-*` `--success` `--elev-*` `--chart-*` `--mask-*` |
| **B-slot** | 品牌方或 schema 别名 | 品牌必须声明 | `--fg-2 → var(--fg)`、`--surface-warm → var(--n-100)`、`--line → var(--border)` |
| **C-extension** | 品牌专属 | 允许列表内自由使用 | `--accent-soft` `--accent-line` `--accent-wash`、`--row-h-dense`、`--statusbar-h` |

## 2. 迁移目标令牌速查（54 处会用到这些）

本清单涉及的**全部**目标令牌。前端只需实现这批，无需发明新令牌。

| 场景 | 目标令牌 | 浅/暗 |
|---|---|---|
| 页面底 / 卡片 / 内嵌区 | `--bg` `--surface` `--surface-sunken` | 自动 |
| 主文本 / 次级 / 三级 | `--fg` `--muted` `--meta` | 自动 |
| 边框 三档 | `--border` `--border-soft` `--border-strong` | 自动 |
| 强调色 三档 | `--accent` `--accent-soft` `--accent-line` | 自动 |
| 语义色 三元组 | `--success/-bg/-bd`、`--warn/-bg/-bd`、`--danger/-bg/-bd`、`--info/-bg/-bd` | 自动 |
| 中性阶（特殊用途） | `--n-400`（placeholder / 禁用前景 / 中性标记）、`--n-150`（斑马纹） | 自动 |
| 层级阴影 | `--elev-1` `--elev-2` `--elev-3` `--elev-4` `--scrim` | 自动 |
| 图表系列 | `--chart-1` … `--chart-5`、`--chart-grid`、`--chart-axis` | 自动 |
| 骨架屏 | `--mask-fill` `--mask-sheen` | 自动 |

**关键性质**：以上**全部为单令牌双主题**（一个名字，浅/暗自动切换）。因此迁移后**组件层零主题判断** —— 所有 `isDark ? A : B` 的 JS 分支都应消失。这正是 Token 化的验收标志。

## 4. 校验方法（F3 可机械核验）

### 4.1 门禁脚本（可直接跑）

```bash
# ① 组件层不得出现非白非黑的颜色字面量（唯一例外 #fff / #000 及其透明度形式）
#    扫描 src 下组件与样式，排除令牌定义文件
grep -rEn "#[0-9a-fA-F]{3,8}\b" src/ \
  --include=*.jsx --include=*.js --include=*.css \
  | grep -v "src/design-tokens.css" \
  | grep -vEi "#(fff|ffffff|000|000000)\b"
# 期望输出：空

# ② 组件层不得出现 rgba()/rgb() 字面量（白/黑透明度例外）
grep -rEn "\brgba?\(" src/ --include=*.jsx --include=*.js \
  | grep -vEi "rgba?\(255,\s*255,\s*255|rgba?\(0,\s*0,\s*0"
# 期望输出：空

# ③ styles.css 不得再定义令牌变量（令牌只在 design-tokens.css 定义）
grep -nE "^\s*--[a-z0-9-]+\s*:" src/styles.css
# 期望输出：空（除 --font-feature-ui 之类的局部例外，需在 PR 里说明）

# ④ 破损声明（精确模式，零误报）
grep -rEn "rgba\([^()]*\),[[:space:]]*0?\.[0-9]+\)" src/*.css
# 期望输出：空

# ⑤ 未定义变量引用
grep -rEn "var\(--radius\)|var\(--gap\)" src/*.css
# 期望输出：空

# ⑥ 第二套语义色板清零（F3 独立硬验收，见 §4.5）
#    该色板有**两种存在形式**，必须都查，否则门禁会静默通过：
#      (a) rgba() 形式 —— styles.css 13 处，RGB 三元组形式，**没有 hex**，按 hex 查会得到 0 命中的假通过
#      (b) hex 形式    —— ScheduleView.jsx 3 处
#    必须加 -i（大小写不敏感），否则 ScheduleView 的 #C98A2B / #C0564B 会漏
grep -rEni "rgba\(\s*(63,\s*166,\s*106|201,\s*138,\s*43|192,\s*86,\s*75)|#(3a9d5d|c98a2b|c0564b)" src/ \
  --include=*.jsx --include=*.js --include=*.css \
  | grep -v "src/design-tokens.css"
# 期望输出：空。改造前实测 **16 处**（styles.css 13 处 rgba 形式 + ScheduleView.jsx 3 处 hex 形式）
#    → 本脚本已在真实代码上跑过并验证计数为 16，不是"写了没试"
#    更根本的检测方式：任何 rgba(R,G,B,α) 的 RGB 三元组，都必须能在令牌文件中找到同值定义。
```

### 4.3 「100% Token 化」的判定标准（不变量口径）

> **验收口径已于本轮修正（PM 裁定）**。原口径是「已迁移 54 处」，现改为**不变量**：**不存在未迁移的硬编码颜色**。
>
> **为什么要改 —— 计数型验收会失效**：明天有人新增一处彩色，「迁移了 54 处」**仍然为真，但已经违规了**。计数只在快照那一刻成立，作为验收标准必然过期。反过来按"72 处"核对又会误判漏改 18 处（见 §0 勘误）。
>
> **口径修正的直接触发**：我在首轮报错了这个数字（72 → 54）。这个错误本身就证明了"计数型验收不可靠" —— 所以 PM 把验收改成不变量。**§0 的 54 处改为"参考信息"，不再是验收标准。**

F3 验收按下表 6 条逐条判定，**全部满足才算通过**。每条都是"不存在 X"的形式，与代码量无关、不会随新增代码过期：

| # | 判定项（不变量） | 通过标准 | 当前状态 |
|---|---|---|---|
| 1 | 组件层存在颜色字面量 | **不存在**（白/黑及其透明度除外） | 违规 54 处（见 §3 映射表） |
| 2 | 组件层存在主题判断取色分支 | **不存在** `isDark ?` / `data-theme === 'dark'` 的取色判断 | 3 处（`EChart.jsx` L81/82、L170） |
| 3 | 令牌在非令牌文件中被定义 | **不存在**（令牌只出现在 `design-tokens.css` / `.json`） | 2 个旧令牌块（`styles.css` L2–15、L694–707） |

### 4.5 第二套语义色板清零（F3 独立硬验收）

> **PM 裁定（原文）**：列为 F3 硬验收 + 独立指标 ——「第二套未文档化语义色板清零，只允许令牌定义的那一组语义色」。并写明「**只迁移不清理第二套色板，等于没做这件事**」。

**问题陈述**：代码里并存**两套**语义色板。表面看每处都在用颜色、都"有颜色"，所以按"有没有硬编码"去查会发现每处都在引用变量或写字面量，**查不出违规** —— 但把它们并排放就明显不统一。

**该色板有 4 个色值，以两种形式存在（这是它一直没被发现的原因）**：

| 语义 | 令牌层（应保留） | 第二套色值 | 形式 | 出现位置 |
|---|---|---|---|---|
| 成功 | `--success: #1F7A4D` | `#3FA66A` | `rgba(63,166,106,α)` | `styles.css` L378 ×2、L388 ×2 |
| 警告 | `--warn: #96631A` | `#C98A2B` | `rgba(201,138,43,α)` | `styles.css` L376 ×2、L389 ×2 |
| 警告 | `--warn: #96631A` | `#C98A2B` | **hex** | `ScheduleView.jsx` L126 |
| 危险 | `--danger: #B23A31` | `#C0564B` | `rgba(192,86,75,α)` | `styles.css` L365、L377 ×2、L390 ×2 |
| 危险 | `--danger: #B23A31` | `#C0564B` | **hex** | `ScheduleView.jsx` L126 |
| 成功 | `--success: #1F7A4D` | `#3a9d5d` | **hex**（第三种绿） | `ScheduleView.jsx` L126 |

**共 16 处**：`styles.css` 13 处（全部是 `rgba()` 形式）+ `ScheduleView.jsx` 3 处（hex 形式）。

> **口径更正**：我此前报过"9 处"。原因是当时只统计了 `styles.css` 里 `rgba()` 形式的那一组，漏掉了 `ScheduleView.jsx` L126 的 hex 形式，且对 `styles.css` 内部计数有误。**准确数字是 16 处 / 4 个色值**。
> **这个更正同时暴露了门禁设计问题**：如果检测脚本只按 hex 查，`styles.css` 那 13 处会得到"0 命中"的**假通过** —— 因为它们是以 RGB 三元组写在 `rgba()` 里的。§4.1 脚本 ⑥ 已改为同时匹配两种形式，并实测验证过（改造前应命中 16 处）。

**后果**：同一个「警告」语义，在 `.ds-badge` 里是 `#C98A2B`，在 `.warn-text` 里是 `var(--warn)`（`#96631A`）。用户看到的是一组颜色相近但不相同的琥珀色 —— **这就是"颜色看着不统一却查不出违规"的根因**。

**验收标准（两条都要满足）**：

| # | 标准 | 验证 |
|---|---|---|
| 1 | 上表右列 4 个色值在组件层**不再出现**（两种形式都查） | §4.1 脚本 ⑥ 输出为空 |
| 2 | 更根本的：**任何 `rgba(R,G,B,α)` 的 RGB 三元组都能在令牌文件中找到同值定义** | 抽查：随机取 10 个组件层 rgba，其 RGB 都能对应到 `--n-*` / `--accent-*` / `--success-*` / `--warn-*` / `--danger-*` / `--info-*` 中某一组的 base 值 |

> **为什么第 2 条比第 1 条更重要**：第 1 条只清理"已知的" 4 个色值。如果只做第 1 条，下次有人再手写一个 `rgba(200,150,40,.1)` 就又会悄悄形成第三套色板。第 2 条是**结构性的**——它要求"组件层任何颜色都必须能追溯到令牌"，才是真正的清零。
>
> **只迁移不清理第二套色板，等于没做这件事** —— 因为迁移只解决了"字面量"问题，没解决"两套语义色并存"问题。这两件事必须一起做。

### 4.6 语义唯一性：一个语义，一个定义来源（F3 独立硬验收，本轮新增）

> **架构师提出、PM 采纳的验收深化**（原文）：**F3 的验收不是"删掉裸色值"，而是"确认语义只有一套定义"** —— 若把那 16 处换成令牌后，令牌层本身仍有同义的并行令牌（例如新加 `--warn-2`），**问题只是搬了家，不算通过**。

这个要求比"清零硬编码"深一层：**它检查的是令牌层自身的整洁度，而不只是组件层的引用合规度。**

#### 4.6.1 判定标准（三条都要满足）

| # | 断言 | 通过方式 |
|---|---|---|
| 1 | `--success` / `--warn` / `--danger` / `--info` **各只有一个定义来源** | `grep -nE "^\s*--(success\|warn\|danger\|info)\s*:" src/styles.css` 输出为**空**；在 `design-tokens.css` 中每个键出现 **2 次**（浅色 1 + 暗色 1），属预期 |
| 2 | **不存在同义并行令牌** | 扫描同义名黑名单（见 4.6.3），命中为 0 |
| 3 | **颜色域内没有多个令牌共享同一字面量值** | 见 4.6.2 —— 这是最有力的自动化断言 |

#### 4.6.2 最有力的一条：颜色域重复字面量检测

**判据**：在同一主题层内，若两个令牌的**值完全相同且都是颜色字面量**，则它们是一个语义的两个来源 —— 改其中一个，另一个不会跟着变。**正确写法是让角色引用色阶**：`--muted: var(--n-500)`，而不是 `--muted: #6F6C65`。

**关键：必须限定在「颜色域」内比对**。若不分域，`--space-3`・`--radius-lg`・`--text-xs` 三者都是 `12px`、`--weight-read` 与 `--z-modal` 都是 `400`、`--leading-normal` 与 `--icon-stroke` 都是 `1.5` —— 这些是**跨域巧合**，不是重复语义。不限定颜色域会产生约 19 组**误报**，而一个充满误报的门禁会被忽略，等于没有。

```bash
# 颜色域重复字面量检测（EXPERIMENTAL —— 见下方"已实测"说明）
# 思路：提取同层内所有「非 var() 引用」的颜色值，按值分组，报告 >1 个令牌的组
```

**已实测结果（本文件作者在真实 `design-tokens.css` 上跑过）**：

| 层 | 修复前 | 修复后 |
|---|---|---|
| 浅色 `:root` | 4 组重复（`#FFFFFF` ×3、`#15795B` ×2、`#57A88F` ×2、`#6F6C65` ×2） | **0 组**（41 个颜色令牌值全部唯一） |
| 暗色 `[data-theme="dark"]` | 7 组重复（`#46B494` ×3、`#8B8F96` ×3、`#2A2D31` ×2、`#383C41` ×2、`#7C8087` ×2、`#F2F3F5` ×2、`#97D7C2` ×2） | **0 组**（46 个颜色令牌值全部唯一） |

**本轮因此修复了自己的一个缺陷**：暗色层原先用**字面量**写角色令牌（`--fg: #F2F3F5` / `--muted: #8B8F96` / `--border: #2A2D31` …），而浅色层用的是 `var()` 引用 —— **同一套令牌，两层风格不一致，暗色层各值都是双来源**。已全部改为 `var(--n-*)` / `var(--accent-*)` 引用。这是"两个来源"问题的真实案例，也说明这条断言不是理论洁癖，能抓到实际缺陷。

> **修复的连带收益**：改色阶时暗色层的角色令牌现在会自动跟随。修复前若把 `--n-500` 调亮，`--muted` 不会动 —— 这类"改了没生效"的漂移极难排查。

| `--danger` | `--bad` `--error` `--err` `--critical` `--red` `--fail` `--negative` `--destructive` `--danger-2` `--danger2` |

### 4.7 门禁脚本自检要求（本轮血的教训）

> **本节规则来自本轮三次真实事故**，请 F3 核对者务必执行。

本轮我在自己写的校验脚本上连续踩了三次「**写了但匹配不到**」的坑，三者的共同点是 —— **失败看起来像通过**：

| # | 事故 | 表现 | 教训 |
|---|---|---|---|
| 1 | emoji 正则用 `\x{...}` 花括号语法 | 在 .NET/PowerShell 中**抛异常**，异常被吞后返回 0 命中 → 每个文件都"通过" | 换语言后正则方言会变；**异常必须显式抛出**，不要静默 catch |
| 2 | 我写进文档的 U+2605（星号）/ U+26A0（警告符号） | 首次扫描报告 0 命中，换 .NET 原生转义后才发现 | 一个"永远返回空"的检测器无法自我证明 |
| 3 | 第二套色板检测按 **hex** 写 | 但那 13 处是 `rgba(63,166,106,α)` **RGB 三元组**、根本没有 hex → 返回 0 命中 | 同一语义可能有多种书写形式；**先枚举形式，再写模式** |

**强制流程（两条，缺一不可）**：

1. **每条门禁脚本必须在「改造前」的代码上先跑一次，确认能命中**。若在改造前都返回空，这条规则等于不存在 —— 它永远不会告诉你任何事。
   - 例：第二套色板脚本在改造前应命中 **16 处**；`--radius` 未定义变量应命中 **8 处**；组件层颜色字面量应命中 **54 处**。
2. **脚本必须显式失败**。用 `grep` 时注意：`grep` 无命中返回退出码 1。若脚本写成 `grep ... | tee` 或包在 `if` 里而忽略退出码，会被误判为成功。**建议每条断言写成"无命中才算通过"的显式判定**，而不是依赖"输出为空"的人工观察。

> **一句话**：**一个从不报警的门禁，和一个从不故障的烟雾报警器一样可疑。**

## 5. 新增令牌的纪律

### 5.1 规则

1. **新组件不得发明新令牌。** 先查 §2 速查表；缺什么先在现有档位里挑（例如"禁用态背景"用 `--surface-sunken`，"边界提示"用 `--info-bg`）。
2. 确实需要新令牌时，**必须同时更新两处**（`design-tokens.css` + `design-tokens.json`）并在 PR 里说明理由与替代方案为何不可行。
3. **禁止同义令牌**。已有 `--border`，不得再建 `--line`（那是 B-slot 别名，应写成 `--line: var(--border)`）。
4. 令牌按**用途**命名，不按色相命名：`--accent` 不叫 `--green`。

### 5.2 本轮判定：档位系统界面**不需要新增任何令牌**

PM 同步的档位（`privacy_mode`）相关界面，我逐一核对了状态需求，结论是**全部可复用现有令牌**：

| 需求 | 复用令牌 | 为何不需要新令牌 |
|---|---|---|
| 档位指示器（顶栏） | `--muted` + `--surface-sunken` + `--border` | 三档**刻意不做颜色编码**（理由见 `03-UIUX.md` §20.2） |
| 档位选择器的选中态 | `--accent-soft` + `--accent` + `--accent-line` | 与既有 `.chip-active` / `.seg-on` 同构 |
| 被档位阻断（4030） | `--warn` / `--warn-bg` / `--warn-bd` | 归入既有「降级/边界」语义组 |
| 隐私与数据路径披露 | `--info` / `--info-bg` / `--info-bd` | 归入既有「常驻事实陈述」语义组 |
| 知识库文档禁用态 | `--surface-sunken` + `--n-400` + `opacity` | 与既有 `.nav-disabled` / `.btn:disabled` 一致 |
| **顶栏「N 项被阻断」徽标** | `--surface-sunken` + `--border` + `--fg` + `--font-mono` | **闭环验证**：按 PM Q1 约束改为中性（不用 `--warn`）后，仍未需要新令牌 —— 既有中性组足够 |
| **知识库「档位受限」说明条** | `--surface-sunken` + `--border` + `--fg` + `--muted` | 同上，同为「持续状态」组 |
| **档位变更历史（P1）** | `--meta` + `--muted` + `--font-mono` | 只读列表，无特殊状态 |
| 解锁引导入口 | `--accent`（文字按钮） | 与既有 ghost 按钮一致 |
| 切档确认弹窗 | `--elev-4` + `--scrim` + `--radius-lg` | 复用既有浮层规范 |

**这本身是一个验收信号**：如果一套令牌体系需要为新界面不断加令牌，说明它的抽象层次错了。档位界面能零新增令牌落地，说明 Phase 1 的令牌划分覆盖到了正确的粒度。

> **加粗的三行是"事后回归"**：PM Q1 约束要求把"被阻断"状态从 `--warn` 改为中性（§20.2 决策三），而档位变更历史是 P1 新增。这两处变更都在设计冻结之后发生，**但它们仍然零新增令牌** —— 说明令牌层的抽象粒度经得住需求变更。这是比"首次落地零新增"更强的证据。

### 5.3 已知偏差（前端实现时需知，勿按字面误解）

本轮自查发现的**一处有意保留的偏差**，前端按下面说明使用即可，不要"纠正"：

| 项 | 说明 |
|---|---|
| **暗色层 `--n-400` 不与 500 保持亮度单调** | 暗色层 `--n-400: #6A6E75` **比** `--n-500: #8B8F96` **更暗**，破坏了"索引越大越暗"的阶梯。原因：`--n-500` 承担 `--muted`（需对 `#0F1011` 达 5.87:1，故必须够亮），而 `--n-400` 承担「禁用 / 占位」，**语义上必须比 muted 更暗**。这是**刻意的角色索引**，不是笔误 |
| 前端应该怎么做 | 占位符 / 禁用前景仍用 `--n-400`（两个主题下都拿到正确观感：浅色下是低对比的灰，暗色下是暗灰）。**不要为了"让阶梯单调"而把暗色 `--n-400` 改亮** —— 那会让禁用态在暗色下反而比正文更显眼 |
| 推荐的后续清理（非本轮） | 把「禁用 / 占位」从色阶里独立出来，新增 A2 角色令牌 `--fg-disabled`（浅色 `#A6A39C` / 暗色 `#6A6E75`），使 `--n-*` 恢复为纯亮度阶梯。**本轮不做**：前端已按冻结基线开工，改动令牌语义的中途变更成本高于收益；登记为技术债 |

> 这一条的存在本身说明一件事：**令牌的"阶梯"与"角色"两种组织方式有内在张力**。本项目选择"色阶 + 角色（Role）双层"，角色层允许引用色阶的**非相邻**档位 —— 因此色阶的单调性只对色阶自身负责，不约束角色映射。这是有意的架构取舍，已在此写明以免后来者误改。
