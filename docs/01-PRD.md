### 0.1 现状能力边界（实测，禁止虚构）

已落地且可演示（不得在后续文档中夸大或缩水）：

- **接入**：CSV / Excel / JSON / 日志 / HTTP API / 数据库代理（`server/db-proxy.mjs`，3.5KB，可选自部署）
- **解析**：Web Worker + `File.stream()` 流式解码，>8MB 自动流式，实测 56 万行 / 15MB ≈ 8.9s，带进度 / 取消 / 采样
- **引擎**：`engine/` 14 个职责模块；类型推断、质量诊断、透视表、相关性、同环比、Top N、时间趋势、列画像、异常、预测、多表 join/merge
- **图表**：ECharts 5，智能推荐 8 类 + 手动图表 + 中国地图
- **AI**：OpenAI 兼容 `/v1/chat/completions`，用户自配 baseURL + Key（默认存 localStorage），未配置时降级内置规则引擎
- **Text-to-SQL 闭环**：自然语言 → SQL（LLM 或规则）→ `sqlGuard` 只读白名单 → `alasql` 真实执行 → 结果表 + 图表
- **模板库**：`matchTemplate` 跨表语义角色映射，模板仅含配置不含原始数据
- **报告导出**：HTML / PDF（系统打印）/ Word / PPTX / Excel / CSV
- **其他**：暗色模式、定时调度（localStorage + 前端轮询，**演示级非真实 cron**）、多数据集工作台、IndexedDB 落盘
- **工程**：Vitest 94 项单测、ESLint/Prettier、CI（lint + test + build）、src 行覆盖 56.7%

**已知破损 / 薄弱点**（决策 4「修复破损」的靶点）：

1. **无后端** → LLM Key 明文留存在 localStorage；多端不同步；无法做服务端会话、知识库、真实调度
2. **AI 能力停留在"生成 SQL 文本"** → 无多轮上下文、无记忆、无口径沉淀，与行业差评中的"一问一答、用完即弃"同病
3. **定时调度是演示级** → 页面关闭即失效，无真实触发与推送
4. **设计系统未落地** → 视觉与交互缺统一规范；`App.jsx`（236 行）与 `reportExport.js` 单测覆盖 0%
5. **RAG 能力为零** → 无文档知识库，模型不认识用户的业务术语与口径
6. **Text-to-SQL 仅支持单表** → 多表需 join 的问题直接拒绝

## 1. 产品定位

### 1.1 一句话定位

> **一个"分析明细不出本机、口径可沉淀、SQL 可审计"的 AI 数据分析 Agent**：把十万行级文件接入 → 清洗诊断 → 智能图表 → 多轮追问 → 多格式报告的完整闭环，跑在浏览器 + 一台可自托管的 FastAPI 后端上。

### 1.2 隐私承诺口径（精确定义，禁止简写）

> **本节的表述口径与 `docs/02-架构.md` 文末「隐私卖点的正面回答」严格一致。任何下游文档不得回退为"数据不出本机"这类绝对化说法。**

原绝对化卖点「原始数据不出本机」**在引入 LLM 的那一刻就已不严格成立**——LLM 调用本身就是数据出本机。后端化没有让它更糟，而是把原本隐含、不可审计的事实变成了显式、可配置、可审计的设计。因此卖点精确化为三条**可验证**的承诺：

| # | 承诺 | 可验证方式（架构依据） |
|---|---|---|
| 1 | **分析明细不出本机，且是架构强制的** | 后端**根本没有接收明细行的接口**：`POST /api/v1/datasets` 只接受 schema + 行数 + sha256（`storageMode` 默认 `local`）。唯一上传通道是用户对某数据集显式执行"上传到本地服务"，且需请求头 `X-Local-Confirm: true` 二次确认。默认模式下 `/query` 直接返回 `code=4090` |
| 2 | **AI 数据去向没变差，反而变得可审计** | 改造前 = 浏览器直连第三方 LLM；改造后 = 浏览器 → 本机 127.0.0.1 → **同一家**第三方 LLM。**最终到达的第三方没有变化**。变化的是：密钥不再落浏览器（消除 XSS 窃取路径）；每次调用都有 token / 耗时 / 成败日志可自查；baseURL 可切成本机 Ollama 实现真正零外传 |
| 3 | **RAG 知识库是唯一"默认出本机"通道，由用户主动发起** | 用户上传文档时，文档分块文本会进入检索上下文并随 prompt 发给上游模型。**上传前必须在 UI 明示**"文档分块会随 prompt 发给上游模型"，不得只写在文档里（设计师须做进交互稿）。**且必须提供事后可查**：用户能筛出"哪些内容实际出过本机"（凭据与谓词见 §6.1 ⑥） |

> **"出本机"的唯一定义**：本条与 §6.1 ⑥ 中的"出本机"，**专指内容被发往上游 LLM / embedding 服务**。以下**均不算**出本机：数据集明细上传到本地 FastAPI（落 127.0.0.1 的 SQLite）、服务端执行只读 SQL、文档原文件存 `data/uploads/`。详见 §6.1 ⑥ 的范围澄清表。

**用户可控的边界**：新增 `privacy_mode` 三档（见 F0），让用户自己决定边界，而不是由产品单方面决定。

| 档位 | 行为 |
|---|---|
| `strict`（默认） | 后端只做 LLM 代理 + 会话元数据；**阻断 RAG 的入库与检索**；阻断服务端数据集明细上传与执行 |
| `standard` | 放开 RAG 知识库（入库 + 检索），文档是用户主动选的 |
| `full` | 在 `standard` 基础上，额外允许数据集明细上传到服务端执行 SQL |

**三档之外的两条显式裁定（PM 已确认，列入验收矩阵，勿当作漏测）：**

1. **`strict` 下同时阻断 RAG 的"检索"，不只是"上传"**。理由：检索会把命中的文档分块送进 prompt，与入库同属"用户内容外传"。若只断上传不断检索，那么 `standard` 期间入库的文档会在降级到 `strict` 后被继续外传——档位形同虚设。简化后的档位语义更可解释：**`strict` = 不出本机的功能全关**。
2. **`POST /db-proxy/query` 三档全放行，这是显式裁定而非遗漏**。理由：目标是用户自己指定的数据库，凭证与查询结果均不落服务端存储，属"用户自己的数据出口"而非"我们的存储"。**该端点在三档下的"应放行"必须写进验收矩阵**，否则会被误判为漏测。UI 需注明"此路径不经过本服务存储，但会连接你指定的数据库"。

档位由 `GET /api/v1/meta/capabilities` 返回；读写档位经 `GET` / `PUT /api/v1/settings/privacy-mode`（写操作需 `X-Local-Confirm`），阻断统一返回错误码 **4030**。前端据此决定功能显隐与降级提示。

> **降级不删数据**：`full` → `strict` 降级**不删除任何既有数据**（本机安全策略禁止删除，删用户数据也不该是切档位的副作用）。既有数据保留、仅阻断访问，并由后端如实暴露 `blocked_by_downgrade: {server_datasets, knowledge_bases, kb_documents}` 计数，供 UI 提示"你有 N 个数据集 / 知识库在当前档位下不可用"。**禁止静默屏蔽**——用户必须知道自己有东西被挡住了。

> **文案执行落点**：界面上任何涉及数据流向的表述，以 `docs/03-UIUX.md` §20.7 **文案禁用表**为准——明令禁用「数据不出本机」「零外传」「部分功能不可用」「数据将被清理」「为了您的安全」等表述。**新文案写完后须对照本节三条承诺逐条检查，对不上就不该出现。**

> **档位不做颜色编码（设计裁定，PM 认可）**：三档在视觉上刻意不区分颜色（不用绿=安全 / 红=危险）。理由：**颜色会引入价值判断**——`strict` 是默认档、最私密档，不是最差档；给 `strict` 配绿等于暗示"放松隐私 = 好"，给 `full` 配绿又会让 `standard` / `full` 用户觉得自己在做错事。三档是用户对边界的**自主选择**，不是优劣排序，故表现形式相同、仅文字不同。

### 1.3 差异化定位（凭什么存在）

相对竞品的三条硬差异，全部从差评反推（推导过程见 §5）：

| 差异点 | 具体含义 | 对照的竞品缺陷 |
|---|---|---|
| **隐私可控的 AI**（而非笼统的"隐私优先"） | 按 §1.2 三条承诺执行：明细不出本机是**架构强制**；AI 数据去向**可审计**；RAG 出本机**由用户主动发起且 UI 明示**；边界由 `privacy_mode` 三档交给用户 | Julius / Hex / Deepnote 必须把原始文件传上云；Metabase / Quick BI 的 AI 能力锁在付费墙或需手动配置词典；DataFocus 的"只发 schema 不发数据"叙事值得借鉴但未给用户可控档位 |
| **可信优先的 Text-to-SQL** | 生成的 SQL 强制经只读白名单校验、**可查看 / 可复制 / 可手改 / 可重跑**，结果标注置信度与口径来源；口径与术语沉淀进知识库，而不是每次从零猜 | ChatBI 全行业差评集中在幻觉 SQL、口径混乱、不可复现、不可审计 |
| **双形态、可自托管** | **本地服务增强模式**（起 FastAPI，解锁 AI / 记忆 / 知识库 / 真实调度）+ **纯前端降级模式**（后端离线时原有 9 视图与全部本地分析能力 100% 可用）。全部开源可自托管，无按席位订阅 | Superset / Metabase 自托管要自己扛运维与升级；商业 BI 按人头收费且价格陡峭、不公开 |

> **双形态是硬验收项**（架构文档 §10.1）：后端离线时前端功能完整性必须由测试专门覆盖。不写"零部署纯前端"作为唯一形态，也不删掉纯前端能力。

### 1.4 定位不做的事（战略克制）

不做"企业级 BI 平台"，不做"取代 Tableau / Power BI"。定位是**个人与 5–50 人小团队的"数据到结论"最短路径工具**，以及**一个能讲清 Agent 工程链路（网关 / 记忆 / RAG / 调度）的可验证作品**。

### 画像 A（主要）：小团队里的"事实上的数据分析师"

| 维度 | 描述 |
|---|---|
| 身份 | 5–50 人公司的运营 / 增长 / 财务 / 业务分析岗；或独立开发者、外包承接方 |
| 年龄 / 技术水平 | 25–38 岁；会用 Excel 透视表和 VLOOKUP，**不会写 SQL**，不懂数仓 |
| 典型场景 | 每周从业务系统 / 平台后台导出 CSV 或 Excel（几千到几十万行），要回答"这个月为什么跌了""哪个渠道最好""哪些客户要掉了"，再拼一份给老板 / 客户的报告 |

| 成功定义 | 30 分钟内从"手上这份导出文件"到"一份能发出去的报告"，且**明细数据始终留在本机**（发给模型的只有 schema 与统计量，可按 §1.2 承诺逐条核验） |

### 3.1 直接竞品

### 3.2 替代方案（用户"将就用"的现有解法）

| 替代方案 | 定位 | 用户为什么用它 | 核心痛点 | 可借鉴点 |

| **Excel / 飞书多维表格 + 公式** | 事实标准 | 零学习成本、人人都有、协作方便 | 上千行、文件 >2M 后**卡顿严重**；公式 `FILTER / COUNTIF / SUMIF` 触发服务端全量扫描，慢查询（单个 FILTER 输出超 20,000 条直接报错）；**图表类型少（无瀑布图）**；**缺数据透视表等分析功能**；学习成本高、功能入口深；移动端功能缺失；与 Excel 公式兼容性有限 | 表格是用户最熟悉的交互隐喻；协作与分享是刚需 |

| **ChatGPT Advanced Data Analysis / Claude Artifacts** | 通用大模型的数据分析模式 | 已有订阅、便宜、会写 Python | 单次会话、**无可复现的资产**；无治理、无权限、无口径；图表非 BI 级；数据上传云端 | 跑真实代码算数而非"估计"算数 |

## 4. 核心功能与优先级（RICE + 横切约束）

### 4.1 RICE 评分标准

| 维度 | 评分范围 | 说明 |
|---|---|---|
| Reach | 1–10 | 每季度受影响用户数（1 = 极少，10 = 全部用户） |
| Impact | 0.25 / 0.5 / 1 / 2 / 3 | 对单个用户的影响（3 = 巨大，0.25 = 微小） |
| Confidence | 50% / 80% / 100% | 确信度（100% = 有数据或基线支撑，50% = 凭直觉） |
| Effort | 1–10 | **锚定量表，单位为"人日 / 人周"，不是"人月"**。见下方锚点表 |

**Score = (Reach × Impact × Confidence) / Effort**，评分越高优先级越高。

**Effort 锚点表（v2.2 新增，用于消除单位歧义）**

| Effort | 折算工作量 | 参照 |
|---|---|---|
| 1 | ≈ 0.5 人日 | 半天可完成的配置 / 文案类改动 |
| 2 | ≈ 1 周（5 人日） | 单模块、小范围接入 + 测试 |
| 3 | ≈ 1.5 周 | 单模块 + 跨 2–3 处接入 |
| 4 | ≈ 2 周 | 单功能闭环（含前后端 + 测试） |
| 5 | ≈ 3 周 | 中等功能，含基础设施 |
| 6 | ≈ 4 周 | 中等偏上功能，含持久化与迁移 |
| 7 | ≈ 6 周 | 大型模块，含后台任务 / 外部依赖 |
| 8 | ≈ 2 个月 | 多模块协同 |
| 9 | ≈ 2.5 个月 | 平台级改造 |
| 10 | ≥ 3 个月 | 重构级投入 |

> **为什么必须显式锚定**：原表述写的是"人月投入（1 = 半天，10 = 3 个月以上）"——端点与人月自相矛盾（1 = 半天不可能是 1 人月），导致同一分值既可读作 3 人日也可读作 3 人月，**偏差可达 10–30 倍**，会直接扭曲 F0 与 F1/F2/F3 的排期竞争。架构师在 F0 估算复核时提出该问题，此处已修正。**本 PRD 中所有 Effort 分值一律按上表解读。**

#### 4.2.2 P0 横切约束 / 契约（**不参与功能排序**）

| # | 约束项 | 性质 | Reach | Impact | Confidence | Effort | Score | 依赖 | 验收 |
|---|---|---|---|---|---|---|---|---|---|
| F0 | **隐私档位 `privacy_mode`**：`strict`（默认，后端只做 LLM 代理 + 会话元数据，**阻断 RAG 的入库与检索**、阻断服务端数据集）/ `standard`（放开 RAG 知识库）/ `full`（再放开数据集明细上传）。**单一判定真相源 `PrivacyPolicy`，三类消费点**（路由级 dependency / 请求体级校验 / capabilities 派生）；档位经 `GET`+`PUT /api/v1/settings/privacy-mode` 读写，阻断统一错误码 **4030** | 横切策略 / 契约 | 10 | 2 | 80% | 2 | **—**（不参与排序） | **依赖 F1 的 `capabilities` 契约；闸控 F7 / F9；档位 UI 依赖 F3** | 见 §6.1 F0 六条验收 |

> **为什么 F0 不参与排序（方法论说明，非免责声明）**
>
> RICE 有两个隐含前提，F0 两条都不满足：
>
> 1. **前提一：被排序项相互独立。** F0 与 F1 恰恰不独立——它消费 F1 的 `capabilities` 契约，又去闸控 F7 / F9。**不同尺度的非独立项放在同一张表里排序，本身就是无效运算**，此时 Impact 取几都没有意义。所以正解不是调 Impact，而是**不把它放进这张表**。
> 2. **前提二：Effort 越低越"便宜"。** F0 的 Effort = 2 是**因为它只是薄薄一层、架在 F1 / F7 / F9 之上**。若这三个还不存在，F0 单独交付出来**用户什么都拿不到**。它的 Effort 低不等于它该排第一，这个数在结构上就是误导的。
>
> **原则：横切项不与功能项同尺度排序。** 因此 F0 上表只保留诚实的 Impact = 2，Score 记「—」，不参与排序；**F1 仍是 Score 第一的功能项**。同时用「**依赖**」列把 F0 与 F1 / F7 / F9 的箭头写进表内——**依赖箭头能承受被误读，脚注不能**。
>
> **F0 的 Effort = 2 有一个前置条件（重要）**：**仅在 F1 已存在的前提下成立。** 若排期上 F0 早于 F1 开工，它需要自建 `capabilities` 端点与鉴权骨架，真实 Effort 会显著上升——这是"非独立项共享 Effort"的典型陷阱。**排期上 F0 不得早于 F1。**

> **F0 的 Effort 修订记录（v2.2）**：v2.1 时估为 3（≈1.5 周），架构师按实现分解复核后给出租略：`PrivacyPolicy` + deps + settings 端点 + capabilities 派生 ≈ 0.5–1 人日；6 处路由级闸门 + 2 处请求体级校验 ≈ 0.5 人日；调度 service 层二次校验 ≈ 0.25 人日；3 档 × 8 端点矩阵测试 + 同源性断言 ≈ 0.5–1 人日；前端档位 UI ≈ 1–1.5 人日。**合计约 2.75–4.25 人日 ≈ 1 周**，对应本表 Effort = 2（原 3 偏高）。**UI 留在 F0 内不拆分**——F0 是可交付项，拆出去会让责任归属模糊。

> **F0 为什么必须交付（尽管不参与排序）**：它是**让 §1.2 三条隐私承诺可验证的唯一机制**。没有 F0，"明细不出本机"就只是默认行为，而非用户可控、可审计的边界。它随 F1 同批交付。

> **关于排序的一处有意偏离（说明，非失误）**：F4「大文件与首屏性能优化」RICE 为 4.50，名义上高于 F3 的 4.00 与 F5 的 2.56。但现状基线已达标（56 万行 / 15MB ≈ 8.9s、主线程不卡顿），F4 本轮的真实定位是**"防劣化"（新引入的设计系统与后端不得拖慢首屏）**，而非"从 0 到 1 的突破"。故保留其高 RICE 分数，排期下调至 P1 首项，让 P0 的三个名额给到"没有就不成立"的地基项（F1）与差异化卖点项（F2）以及全局可见的 F3。

### 4.3 MVP 范围

**MVP = P0 功能三项（F1 / F2 / F3）+ P0 横切约束 F0（随 F1 同批交付）**，判定理由：

- **F1 LLM 网关是单点前置**：没有它，F2 的多轮上下文、F6 的记忆、F9 的 RAG、F5 的服务端导出、F7 的服务端执行全部无从谈起；同时它直接解决现状"Key 明文存前端"的硬伤。**F1 是本轮的真正地基，也是 Score 最高的功能项（6.00）。**
- **F2 是唯一的产品差异化**：行业差评最高的三个词是"幻觉 / 口径 / 不可复现"，F2 是唯一直接回应的功能。
- **F3 是全站可见的地基**：决策 4「修复破损 + 设计系统落地」是用户明确点名的范围，且它是所有前端改动的公共依赖；它同时承载"双形态可见状态条"（后端在线 / 离线），这是 §4.4 双形态承诺的 UI 落点。
- **F0 是让隐私承诺成立的前提**：§1.2 的三条隐私承诺若没有 F0，就只是"默认行为"而非"用户可控、可审计的边界"。它不参与功能排序（见 §4.2.2 的方法论说明），但必须在 P0 内交付。

**排期硬约束：F0 不得早于 F1 开工**（F0 的 Effort = 2 以 F1 已存在为前提，否则其需自建 `capabilities` 与鉴权骨架，真实 Effort 显著上升）。

**P1（次轮）**：F4 性能优化 → F5 报告导出增强 → F6 会话与记忆 → F7 数据服务与调度 → **F0 补充：档位变更历史**
**P2（后续）**：F8 分析能力增强 → F9 RAG 知识库检索

> **档位变更历史的定级说明（PM 裁定）**：设计师提议增加"用户可回看的档位变更列表"（`privacy_mode_changed` 事件已含 from/to，数据基础具备）。**裁定：做，但列 P1，不进 P0。** 理由——它服务于 §1.2 承诺 2 的"可审计"，且成本低（只读列表，复用已有事件）；但它**不是 F0 六条验收成立的必要条件**，纳入 P0 会把 F0 的 Effort 从 2 推向 3（当前估算 4–5.75 人日已接近 1 周上限），属"在 P0 内做范围蔓延"。
> **实现约束**：① 只读列表，放在设置页档位区块内，**不新起视图**；② **仅存本地**，不上报任何服务端，不参与埋点聚合（它是用户的私人审计记录，不是分析数据）；③ 与埋点 `privacy_mode_changed` 同源但**用途不同**——埋点用于验证产品假设，变更历史用于用户自查，两者不得混用同一份存储。

> **两条防误读声明**：
> 1. F9 虽列 P2，但**属于本轮决策 2③ 的既定范围，不是 Out-of-Scope**；其排期靠后仅因依赖 Embedding 探针基建与 30 条标注评测集这两项前置投入。
> 2. F9 的检索能力**不承诺"语义检索"为硬需求**：多数"OpenAI 兼容"服务只实现 chat、不实现 `/v1/embeddings`。因此 PRD 统一表述为"语义检索（若 provider 支持）/ 关键词检索（兜底）"，并配套自动降级 + UI 强制徽标。**禁止任何下游文档把"语义检索"写成无条件承诺**，否则验收时会变成不可达需求。

### 4.4 双形态运行模式（对决策 3 / 4 的形态约束）

产品有两种形态，**不是"零部署纯前端"单一形态**：

| 形态 | 触发条件 | 可用能力 |
|---|---|---|
| **本地服务增强模式** | 后端 `GET /api/v1/health` 探测成功（超时 1.5s） | 全部能力：AI 网关、多轮会话与记忆、RAG 知识库、真实 cron 调度与推送、服务端 SQL（受 F0 档位约束） |
| **纯前端降级模式** | 探测失败（用户未启动后端、或后端不可用） | 原有 9 视图 + 全部本地分析能力（文件接入 / 流式解析 / 清洗 / 质量 / 图表 / 工具箱 / 模板 / 本地 Text-to-SQL 执行 / 报告导出）**100% 可用**；仅 AI 记忆 / RAG / 服务端调度不可用，并明示原因与启动指引 |

**硬验收项**：后端离线时前端功能完整性必须由测试专门覆盖（"杀掉后端进程后前端功能完整性"）。**这既是承诺也是回归保护**——用户不装后端也能用，装了后端才有 AI。

## 5. 市场空白结论（全部从差评反推）

### 结论一：存在一条"自助分析的易用性"与"明细数据不出本机"之间的真空带

**推导链**：Metabase 自托管版把 AI 关在付费墙外、且被评价"仍像 SQL-first 工具"，Superset 被业务用户判定为"完全不写 SQL 就用不了"、界面英文且学习曲线陡（Docker + Python），两者都把门槛留给了技术人；另一端，Julius / Hex / Deepnote 的摩擦确实低，但**必须把原始文件交给云端**，Deepnote 被明确点出"云端 notebook 不适合有数据驻留要求的场景"，Julius 的合规结论是"受监管数据上传前需先查 Trust Center，HIPAA 要另签 BAA"。

**空白**：缺一个**默认本地优先、AI 调用只接触 schema 与统计量（明细行不出本机）、且边界可配置可审计**、同时**开箱即用不需要写 SQL / 不需要运维**的产品。DataFocus 用同一套隐私叙事（"只发查询文本与 schema，不发原始数据"）作为差异化，恰好证明这个定位在中文市场被验证过——但它的多轮对话深度被点名为弱项，且未给用户可控的隐私档位，留下了改进空间。

### 结论二：缺的从来不是"能问数"，而是"敢拿它做决策"

**推导链**：ChatBI 的差评高度一致且量化——跨表准确率仅 60%–70%、**上线三个月后周均使用率不足 15%、约八成沦为摆设**、口径混乱导致同一问题返回矛盾结果、幻觉结果不可复现不可审计、只支持"一问一答"而无法形成 What → Anomaly → Why → How → What-If 的闭环。Tableau Explain Data 虽然形态正确（解释异常数字），但限制严苛到"只支持单个标记、单一数据源、维度基数 >500 就不参与分析"；而 Deepnote 的差评也承认"AI 生成的分析仍需人工校验 join、数据泄漏与统计结论"。

**空白**：把**"生成物可审计"做成一等公民**——SQL 可查看 / 可复制 / 可手改 / 可重跑，结果标注口径来源与置信度，确认过的口径与术语沉淀成可复用的长期记忆。让"这次分析"变成**资产**，而不是用完即弃的一次对话（Hex 的差评里唯一被称赞的正是"SQL 与图表是持久、可重跑的资产"）。

### 结论三：数据体量与"最后一公里交付"两头都缺人管

**推导链**：一端，传统工具在数据体量上撞墙——Metabase 被反复点名"大数据集慢、查询超时"，飞书多维表格"上千行、文件 >2M 卡顿严重"且 FILTER 类公式触发全量扫描、单函数输出超 20,000 条直接报错。另一端，"最后一公里"交付同样薄弱——Metabase 的"导出格式少"被列为固定差评项，Julius 的分析结果"不可复现、做不了生产级报表"，通用 chat 工具的产出只是无法重建的截图。

**空白**：在**百万行级文件接入**与**六格式可复用报告输出**之间，缺一个两端都不掉链子的轻量工具。本项目现状已实测 56 万行 / 15MB ≈ 8.9s 且六种导出格式齐备，这一条是**已有优势的延续**而非新增能力。

## 6. 验收标准

### 6.1 核心功能验收（Given / When / Then）

**F1 · LLM 网关与密钥托管**

- Given 服务端未配置任何模型 Key，When 前端发起问数请求，Then 返回 401 与结构化提示（含"去哪里配置"的引导文案），界面展示 Error 态与降级说明，不白屏、不静默失败
- Given 服务端配置了主模型与兜底模型，When 主模型返回 5xx 或超时，Then 自动切换兜底模型并完成回答，调用日志中该条记录标记 `fallback_from`
- Given 配置了 3 个模型，When 分别发起"代码 / 分析 / 摘要"三类任务，Then 路由到任务类型匹配的模型，日志可直接验证
- Given 一次完成的分析请求，When 查看调用日志，Then 记录包含 `request_id / model / tokens_in / tokens_out / latency_ms / status`，且 Token 数与模型返回的 usage 误差 < 1%
- Given 前端页面，When 检查 localStorage 与网络面板，Then 不存在 LLM 明文 Key

**F2 · Text-to-SQL 可信闭环增强**

- Given 用户提问"2024 年各省销售额前 10"，When 生成并执行，Then 展示生成的 SQL、结果表、图表、中文解释、口径来源（引用了哪个知识库条目）
- Given 生成的 SQL 含 `DROP` / `UPDATE` / `DELETE` / 多语句，When 点击执行，Then 被拦截，并明确指出命中的违规关键字，不执行任何语句
- Given 生成的 SQL 含不存在的列名，When 提交，Then 提示"未识别的列：X"，并列出该表可用列
- Given 用户手动修改了生成的 SQL，When 点击重跑，Then 以修改后的 SQL 执行，结果与直接提问同样展示口径来源
- Given 连续 5 轮追问（"上个月销售额" → "那华东呢" → "为什么跌了" → "哪个品类" → "如果砍掉 A 品类会怎样"），When 逐轮提问，Then 第 5 轮仍正确继承"上个月""华东"等前文实体与筛选条件，且界面显示当前生效的上下文指示

**F3 · 前端设计系统落地 + Linear 式布局**

- Given 全站任意页面，When 运行 Token 校验脚本（`docs/03-UIUX-附录A-Token清单.md` 的 5 条 grep），Then **非令牌颜色字面量命中 0 处**（允许例外仅 `#fff` / `#000` 白黑两色）
- **验收口径是「不变量」而不是「数量」**：判据为「**不存在未迁移的硬编码颜色**」，**不是**「已迁移 54 处」。原因——硬编码数量会随代码变化而失效（新增一处颜色，"迁移了 54 处"仍为真但已违规）；且设计师首轮曾把口径报为 72 处、逐行清点后更正为 54 处（其中旧令牌定义块 32 处属整块删除、白黑例外 15 处属允许保留，均非"迁移点"）。**若验收写成"迁移 72 处"，核对者会去找 72 个点、只找到 54 个，误判为漏改 18 处。** 载量以附录 A 为准
- Given 迁移完成，When 审查令牌层自身，Then **语义只有一套定义**：
  - **每个颜色令牌在同一主题层内取值唯一**（不存在两个颜色令牌共享同一字面量值）。**断言必须限定在"颜色域"内比对**——不分域会产生约 19 组跨域误报（`--space-3` / `--radius-lg` / `--text-xs` 都是 `12px`；`--weight-read` 与 `--z-modal` 都是 `400`；`--leading-normal` 与 `--icon-stroke` 都是 `1.5`），这些都是跨域巧合而非重复语义
  - `--success` / `--warn` / `--danger` / `--info` **四个语义键各只有一个定义来源**，且**不存在与其同义的并行令牌**（`--ok` / `--bad` / `--amber` / `--warning` 等须零命中）
  - **断言是"语义唯一"，不是"删掉裸色值"**：若把第二套未文档化色板的裸色值换成令牌后，令牌层本身仍存在同义的并行令牌（如新加 `--warn-2`），**问题只是搬了家，不算通过**。第二套色板以**裸 `rgba()` 三元组**形式存在（**不是 hex**——故按 hex 写的检测会全部漏报，这是设计侧自检抓到的第三类"写了但匹配不到"），它与 `--success` / `--warn` / `--danger` **不是同一组颜色**，是"颜色看着不统一"的真正根因。**具体处数与行号以附录 A §4.6 为准，此处不写死数字**
  - **同一套令牌不得出现"两层两种写法"**：浅色层用 `var()` 引用、暗色层却用字面量 = 每个值都是双来源。实测该断言立即抓出暗色层 7 组重复（修复后浅色 41 个颜色值全唯一、暗色 46 个全唯一）
- Given 导出物（报告 HTML / PDF / Word / PPTX / Excel / CSV），When 审查其颜色定义，Then **颜色同样来自同一令牌源，不存在为导出物单独写死的语义色**——导出物是用户可见产物，独立写死的语义色是**第三套并行定义**，属同一类问题。**范围界定**：本条只要求"单一定义源"，**不要求重做导出模板的视觉设计**（那会溢出 F3 的 Effort）
- Given 每一条门禁脚本（Token 5 条 grep / 契约 `check_contract.py` / `privacy_mode ==` 单一真相源 / 架构文档结构锚点），When 在**改造前的代码**上先跑一次，Then **必须命中**（用于证明它"能响"），且**脚本必须显式失败**（退出码 / 断言），不得依赖"输出为空"的人工观察。
  - **性质说明（避免与上面"不变量口径"混淆）**：这里的"预期命中数"是**一次性的校准基线（已知阳性样本）**，用来证明门禁有效，**不是验收阈值**——验收阈值一律是"0 处"。校准基线以 `docs/03-UIUX-附录A-Token清单.md` §4.7 记录为准（含第二套色板、`--radius`、组件层字面量各项的改造前命中数），PRD 不复制具体数字以免再制造一份会失真的计数
  - 理由：设计师在自写校验脚本上**连续踩了三次"写了但匹配不到"**，共同点是**失败看起来像通过**——① `\x{...}` 在部分运行环境抛异常后静默返回 0；② 文档中引用的两个特殊字符首扫未发现（该轮又复现一次）；③ 第二套色板实际是 `rgba()` 三元组、根本没有 hex，按 hex 写的检测全部漏报
  - **判据**：**一个从不报警的门禁，和一个从不故障的烟雾报警器一样可疑。** 门禁必须被证明"能响"才算门禁
- Given 任意列表 / 表格视图，When 操作表头，Then 支持列排序、列筛选、列显隐自定义，且状态在会话内保持
- Given 任意页面，When 按下 Cmd/Ctrl+K，Then 唤起全局搜索，可跳转全部主视图与最近数据集
- Given 任意删除操作（数据集 / 模板 / 会话 / 调度），When 点击删除，Then 弹出二次确认，确认后可从 toast 撤销
- Given 档位界面新稿，When 统计新增令牌，Then **新增令牌数为 0**（新界面的每个状态需求均复用既有令牌）。**这是一个抽象层次的验收信号**——若一套令牌体系需要为每个新界面不断加令牌，说明抽象层次错了，应回溯令牌设计而非继续加
- Given 一次 `npm test`，When 执行完毕，Then 94 项以上全绿，`vite build` 无新增警告，`eslint .` 0 error

> **门禁与筛选器的可信度（本 PRD 的一条横切判据）**：本轮反复出现同一失效模式的两端——
> - **恒真的筛选器**（用 `ingested_mode` 判"是否出本机"）：等于没有筛选器，但用户以为它在工作，**比不提供更坏**；
> - **恒响的门禁**（不做颜色域限定导致 19 组跨域误报）：**一个充满误报的门禁会被忽略，等于没有**；
> - **恒不响的门禁**（写了但匹配不到）：**失败看起来像通过**，比报错更危险。
>
> 三者共同点是**它们都不可信，而不可信的工具会让使用者放弃人工核对**——破坏的不是功能，而是对整套校验的信任。故本 PRD 的验收一律要求"**阈值型断言 + 已证明能响**"，不接受"应该会报"。
- Given 任意列表 / 表格视图，When 操作表头，Then 支持列排序、列筛选、列显隐自定义，且状态在会话内保持

**F0 · 隐私档位 `privacy_mode`（六条验收，前五条可机械核验）**

- **① 闸门矩阵逐格一致**：Given 架构文档 §7.4.1 闸门矩阵（3 档 × 8 受控端点，共 18 格判定），When 逐格实测放行 / 阻断结果，Then **与矩阵逐格一致，无偏差**。矩阵中 `POST /db-proxy/query` 三格为"应放行"，属显式裁定，**不算漏测**
- **② 指引正确性（防漂移 + 防误导）**：Given 任一档位，
  - **同源性**：When 对比 `GET /meta/capabilities` 的声明与各受控端点的实际返回，Then **两者完全一致**。禁止出现"UI 显示可用、点下去返 4030"或"能力其实可用但入口被藏"的双向漂移
  - **4030 载荷正确性**：When 触发档位阻断，Then 断言 `data.required_modes` 与 §7.4.4 capability 映射表中该 `capability` 的档位集合**一致**，且 `data.capability` 落在 4 值枚举内（`kb_ingest` / `kb_search` / `server_dataset_register` / `server_sql`）。**仅断言 `code == 4030` 不够**——如果 `PrivacyPolicy` 给错档位集合，前端会引导用户切到一个仍然不可用的档位，用户会认为整个档位机制是坏的
  - **载荷完备性**：`data` 含 `current_mode` / `required_modes` / `capability` / `setting_path` / `blocked_by_downgrade` 五个字段，**字段恒存在（无阻断数据时为 0，不返回 `undefined`）**，前端免去空值判断
- **③ 单一真相源**：When 执行 `grep -rn "privacy_mode ==" app/`，Then **只命中 `core/privacy.py` 一处**。出现第二处即不合格（该检查比人工看代码可靠，且是可执行的 CI 门禁）
- **④ 绕过前端的入口也覆盖**（两类，不止一类）：
  - Given `strict` 档，When **绕过前端直接构造 HTTP 请求**调用受控端点，Then 被拒并返回 **4030**
  - Given `strict` 档，When **经后台线程入口**（APScheduler 调度器执行一个引用了知识库的任务，不经过 HTTP 路由）执行，Then 由 `schedule_service` 层拦截。**这一条最易漏**——绕过 HTTP 的不只是前端，还有自家的调度器
- **⑤ 降级不删数据且如实暴露**：Given 从 `full` 降级到 `strict`，When 查看既有数据与 `capabilities`，Then 既有数据集 / 知识库 / 文档**均未被删除**，且 `blocked_by_downgrade` 计数与实际被阻断的资源数一致，UI 相应提示"你有 N 个…在当前档位下不可用"。
  - **补充（两个计数不可并列）**：`blocked_by_downgrade.kb_documents`（因档位**不可访问**）与"`egress_at` 非空的文档数"（**曾外传**）**语义完全不同、不可互推**——一篇文档可以同时"被档位挡着"且"从未出本机"（关键词模式下 `standard` 入库、后降到 `strict`）。**把这两个数放在一起展示会让用户得出错误结论**，故 UI 上不并列呈现
- **⑥ 交互流程与"可自查"凭据（非闸门判定，补充）**：
  - Given `full` 档，When 用户对某数据集执行"上传到本地服务"，Then 需携带 `X-Local-Confirm: true` 且经二次确认弹窗，成功后 `storageMode` 由 `local` 变为 `server`
  - Given 文档在 `standard` / `full` 档入库，When 查看知识库列表与详情，Then 该文档按其**实际外传状态**标记为"已出本机"，**并且可被"仅看已出本机"筛选器筛出**——这是"可自查"的核心入口，只做一个徽标不算达标
  - **筛选器谓词必须写作 `egress_at IS NOT NULL`（关键，不可写成"`ingested_mode` 非空"）**。原因见下方"授权凭据 ≠ 事实凭据"。**这是本条唯一的强制措辞。**
  - **凭据字段（依赖架构新增，5 个）**：`ingested_mode`（枚举**仅 `standard` / `full`**，不含 `strict`——`strict` 下入库已被闸门阻断，系统内不可能存在 strict 入库的文档，这是可断言的不变量）、`ingested_at`、**`egress_at`**（内容**实际**离开本机的时间，**NULL = 从未离开**）、**`embedding_sent`**（分块是否**曾经**发往上游 embedding 接口）、`egress_channel`（`embedding` / `retrieval` / `both` / null，供 UI 解释"为什么会出本机"）。**`ingested_mode` 不可省，也不能用"当前档位"替代**——用户可能在 `standard` 入库后切到 `full`，用当前档位标注会错标
  - **档位受限下的预览规则**：`strict` 阻断的是"入库与检索"（内容外传），因此**文档预览保持可用**（文档已在本地 `data/uploads/`，预览不出本机），仅禁用"重新索引""删除"。**不做一律禁用**——那是过度封锁；预览可用也让用户能亲眼确认内容没丢。**边界条件**：若预览路径涉及任何 LLM 调用或重新嵌入（即构成外传），该部分必须一并禁用
  - **状态：已解除阻塞**（架构师已补齐字段与凭据语义，见 `docs/02-架构.md` §7.5）

> **授权凭据 ≠ 事实凭据（为什么 `ingested_mode` 不能作筛选谓词）**
>
> 这是架构师在实现时拦下的一个**系统性误报**，必须写进 PRD 因为它决定了验收措辞：
>
> `ingested_mode` 回答的是"**谁授权入库**"，不是"**内容有没有真的出去**"。两者在下面这个场景必然背离：
>
> - **provider 不支持 `/v1/embeddings` 时（§12 R2，概率标为高），入库降级为 FTS5 关键词模式，分块文本从未发往上游**。此时 `ingested_mode = 'standard'`，**但内容没有离开本机**。
> - 若筛选器用 `ingested_mode` 判定，**整个知识库的每一份文档都会被标成"已出本机"**。这不是个别误标，而是**全库系统性误报，且方向是让用户高估自己的暴露面**。
> - 一个"永远为真"的筛选器等于没有筛选器，但用户会以为它在工作。**按本 PRD 一贯的判据，这比不提供筛选入口更坏**——它会给用户一个假的安全结论。
> - 因为 F9 的"双档"设计（语义 / 关键词）让这个场景**不是边缘情况，而是最常见配置下的默认路径**。
>
> **正确的谓词是"事实上有没有出去"**，故用 `egress_at IS NOT NULL`。
>
> **两条实现约束（做错了会漏报）**：
> 1. **`egress_at` 一经置位永不复位（sticky）。** 数据无法撤回——已发到上游，切回 `strict` 也不会让它回来。**任何"按当前档位重算 `egress_at`"的实现都是缺陷，且错在危险方向（漏报）。**
> 2. **两个置位时机都必须覆盖**：① **入库时**——embedding 成功调用上游，记 `egress_channel='embedding'`；② **检索注入时**——分块被放进发往上游 chat 的 prompt（绑定知识库的会话），若为 NULL 则记 `retrieval`，已是 `embedding` 则升 `both`。**只做第一条即是漏报**，因为第二条才是 `standard` 档下内容外传的主路径。
>
> **范围澄清：本地服务落盘 ≠ 出本机。** 本条及 §1.2 承诺 3 中的"出本机"**专指发往上游 LLM / embedding 服务**：

| 动作 | 出本机？ | 说明 |
|---|---|---|
| 数据集明细上传到本地 FastAPI（`full` 档） | **否** | 落在 127.0.0.1 的 SQLite |
| 服务端执行只读 SQL | **否** | 结果回浏览器 |
| 文档原文件存 `data/uploads/` | **否** | 本机磁盘 |
| 分块发往 `/v1/embeddings` | **是** | 上游服务 |
| 分块进 prompt 发往 chat | **是** | 上游服务 |

> **推论**：`datasets` 表**不需要** `egress_at`。它的外传路径（schema / 统计摘要进 prompt）改造前就存在，不涉及"用户主动上传内容"，不属承诺 3 覆盖范围。若日后要做"全量外传自查"，那是**独立需求**，应收敛到 `llm_call_logs`，**不要在每张业务表上加字段**。

> **机器可校验锚点（不复制契约内容）**：上述 ① / ② / ③ 的判定依据都在架构侧单一定义，PRD **不复制**闸门矩阵与载荷 schema——复制即造出第二份需人工同步的真相源。参照位置：闸门矩阵 `docs/02-架构.md` §7.4.1；4030 载荷与 capability 映射 `docs/api/openapi.yaml` 的 `components/schemas/PrivacyBlockedData` + `components/responses/PrivacyBlocked`（人读版见 `02-架构.md` §7.4.4）；契约门禁 `scripts/check_contract.py`（校验 5 个字段齐备、可复用响应存在、8 个受控端点均声明 4030，当前 `rc=0`）。**若有人删字段或改枚举，门禁会红，不必等人工审码。**

**F1 追加验收（与 F0 共用契约）**

- Given 已切换档位，When 重新请求 `capabilities`，Then 档位与能力声明同步更新且刷新后保持；`PUT /settings/privacy-mode` 缺 `X-Local-Confirm` 时被拒

## 7. 边界条件

### 7.1 通用边界

| 类别 | 要求 |
|---|---|
| **空状态** | 无数据集 / 无会话 / 无模板 / 无调度 / 无知识库时，均给出**真实可点击的下一步引导**，不使用空洞营销文案 |
| **错误状态** | 前端错误 + API 错误统一走 Error 分类（模型 / 网络 / 权限 / 数据 / 未知），每类给出可执行动作 |
| **加载状态** | 首屏骨架屏；长任务（解析 / 导出 / 执行 SQL / Embedding）显示进度百分比与剩余量，均可取消 |
| **边界值** | 行数 0 / 1 / 上限；列数 1 / 超宽；单文件 2GB 硬上限；SQL 结果 5,000 行上限；文本切分块长下限 |
| **并发** | 同一数据集被解析 + 查询 + 导出同时触发时，读操作隔离、写操作加锁；后端 SQL 执行单连接池排队 |
| **离线** | 见 §4.4 双形态：后端离线时进入「纯前端降级模式」，断网仍可完成"文件接入 → 分析 → 报告"（原有 9 视图 + 全部本地能力 100% 可用），仅 AI / RAG / 记忆 / 服务端调度不可用，并明示原因与启动指引 |
| **权限拒绝** | 无后端 token / token 过期 / 非法数据集 ID，一律返回 401/403 + 明确提示，前端回到可操作状态而非卡死 |
| **超时** | LLM 生成 > 30s、SQL 执行 > 10s、导出 > 60s 均超时中止并提示，不阻塞界面 |
| **内容安全** | LLM 输出写入 HTML 报告前一律 `esc()` 转义（现状已实现，须保持）；不采集原始数据行作为埋点属性 |

### 7.2 分功能边界

- **F1**：多模型路由仅在主模型失败时兜底，不做并行竞速（避免重复计费）；密钥服务端加密存储，日志中绝不打印 Key；Token 统计对不返回 usage 的兼容接口按字符数估算并标记 `estimated: true`
- **F2**：首版仍**仅支持单表**查询；多表 join 问题返回明确提示"请先使用关联功能"；LLM 生成的 SQL 必须经白名单校验后才可执行；`alasql` 执行不得使用 `eval` / `Function` 拼执行
- **F3**：主题切换不重跑分析；暗色模式下打印 / PDF 强制浅色；Design Token 变更不得改变任何数值计算路径
- **F4**：硬上限 2GB 单文件，超限直接拒绝并提示分片；非表格文件（图片 / PDF 表格除外）按扩展名 / MIME 预检拒绝；内存软上限 20 万行，超出仅保留采样 + 全量落盘
- **F5**：PPTX 图表数量上限 6 张，超出省略并提示；报告中的数字必须同源自分析结果，**不得重新计算**
- **F6**：会话与记忆持久化在后端；记忆内容可见 / 可编辑 / 可删除；关闭记忆后不得有任何历史注入
- **F7**：调度任务超时上限 10 分钟；同一任务不允许重叠执行（前一次未结束则跳过并记录）；失败重试上限 3 次；数据集明细上传受 `privacy_mode` 闸门约束，`strict` 下接口层直接拒绝
- **F8**：归因结论必须标注是基于统计检验还是基于规则的启发式，不得把相关性表述为因果
- **F9**：RAG 检索结果必须标注引用来源；知识库文档删除后其向量同步删除；**检索模式以 provider 探针结果为准，探针为 false 时自动降级关键词检索并 UI 徽标明示**；上传前必须告知"文档分块会随 prompt 发给上游模型"；要真正零外传需用户自行把 provider 切到本机 Ollama（含本地 embedding）
- **F0**：档位默认 `strict`；判定由**唯一策略对象 `PrivacyPolicy`** 产出，三类消费点（路由级 dependency / 请求体级校验 / capabilities 派生）**不得各自推断**；**后台线程入口（调度器）必须二次校验**，路由级闸门对其无效；档位切换**不改动既有数据的存储位置**（不迁移、不删除、不静默移动），仅阻断访问并如实暴露 `blocked_by_downgrade` 计数

## 8. 明确不做（Out-of-Scope）

| # | 不做项 | 原因 | 何时考虑 |
|---|---|---|---|
| 1 | **用户账号体系 / 多租户 / RBAC 权限模型** | 本轮场景是单用户与小团队自托管，账号体系会显著拖慢核心 AI 能力的验证；且差评显示企业级权限是"重治理"路径，与本项目"轻量最短路径"定位冲突 | 当出现真实的多用户协作诉求、或需要对外提供 SaaS 化服务时；届时按 「组织 → 角色 → 资源」三级模型设计 |
| 2 | **真实生产级数仓连接器（Hive / CDH / 数据湖 / 数据治理）** | Quick BI 的差评已证明"云原生能力深而不广"、CDH 接入需折腾驱动与网关；端到端数据治理成本远超个人项目收益，且与"本机 / 小团队轻量"定位根本冲突 | 当目标客户从个人 / 小团队切换为中大型企业、且必须对接既有数仓时 |
| 3 | **多表（≥3 表）复杂 NL-to-SQL：多表 join、嵌套子查询、窗口函数** | 行业差评明确：跨表准确率仅 60%–70%，硬做会直接砸掉"可信"这一核心卖点；现状单表 + 白名单的策略是**有意的能力克制** | 当语义层与指标模型沉淀成熟、且单表准确率稳定 ≥ 85% 之后，按「单表 → 双表 join → 多表」渐进开放 |
| 4 | **移动端原生 App / 完整移动端适配** | 数据分析（大文件上传、宽表查看、多图表对比）的主战场在桌面；移动端投入产出比低，且飞书多维表格的差评已显示移动端功能缺失是长期难题而非短期可解 | 当出现大量"现场 / 外勤只读查看"需求时，先做只读移动 Web，不做原生 App |
| 5 | **私有化 GPU 推理 / 自托管 LLM 权重的部署工程（vLLM / Ollama 服务端封装）** | 硬件成本（70B 级需 4×A100 级、约 $40K 起）与运维负担在作品阶段不可承受 | 当进入受监管行业客户、或需要完全离线 / air-gapped 环境时。**注意边界**：本项目不封装本地推理服务，但**支持用户把 provider 的 baseURL 指向自己的 Ollama**（含 `nomic-embed-text` 做本地嵌入）——这是产品内明确告知的隐私升级路径，不属 Out-of-Scope |
| 10 | **Docker / 一键容器化部署** | 目标用户是"有 Python 但无 Docker 习惯"的个人开发者；引入容器需要讲清卷挂载、Chroma 单进程约束、SQLite WAL 落盘等一堆运维知识，与"轻量"定位冲突 | 当用户群体扩大到需要团队统一部署、或需要 CI 环境可复现时。当前形态固定为用户 `python run.py` 手启后端 |
| 6 | **实时流式数据接入（Kafka / Flink 实时管道）** | 偏离"文件与批量分析"的核心定位，实时链路会引入完全不同的架构复杂度（背压、水位线、乱序） | 当出现"实时监控 + 阈值告警"这类明确场景时；先做「定时轮询 + 增量对比」作为过渡方案 |
| 7 | **前端 JS → TypeScript 全量重写** | 收益真实但工作量会直接挤压 P0/P1 的功能交付；且现有 94 项单测已提供基础回归网 | 当 P0/P1 功能稳定、进入纯工程优化阶段时，作为独立改造专项推进（按模块渐进迁移，不做大爆炸式重写） |
| 8 | **多用户实时协作编辑（类 Hex / Deepnote 的多人在线 notebook）** | Hex 差评指出其协作虽好但"计算费用与席位分开计价、成本不可预测"；协作不是本项目当前被验证的核心痛点，且需引入 CRDT / OT 级复杂度 | 当团队协作需求被真实反复提出、且账号体系（第 1 项）落地之后 |
| 9 | **可视化大屏 / 对外汇报投屏功能** | 行业差评显示大屏常沦为"墙面装饰"（需专人讲解、领导参观才打开），属低使用率功能；与"高密度分析工作台"的设计方向相悖 | 当出现明确的对外汇报 / 展厅场景时 |

## 10. 数据埋点方案

不埋点 = 上线后无法验证产品假设。以下为 MVP 必须埋点的最小集合。

### 10.1 必埋事件

| 事件类别 | 必埋事件 | 说明 |
|---|---|---|
| 获客 | `page_view`、`app_open` | 新用户从哪来、打开频率 |
| 激活 | `dataset_created`（首次接入成功）、`analysis_completed`（首次产出图表）、`ttfi_measured`（首个洞察耗时） | 定义"首次价值时刻" |
| 留存 | `session_start`、`session_duration`、`return_visit`（次日 / 7 日回访） | DAU / WAU、使用频次 |
| AI 核心链路 | `llm_request_sent`、`llm_response_received`、`llm_fallback_triggered`、`text2sql_generated`、`text2sql_blocked`、`sql_manually_edited`、`sql_rerun` | **本项目的核心验证指标**：AI 真的被用了吗？生成的 SQL 被改了多少次？拦截了多少危险语句？ |
| 记忆与知识库 | `conversation_created`、`conversation_turns`、`memory_viewed`、`memory_edited`、`memory_deleted`、`kb_document_uploaded`、`kb_retrieval_hit` | 验证"记忆 / RAG 是否真的产生价值" |
| 隐私与降级 | `privacy_mode_changed`（含 from/to）、`privacy_gate_blocked`（档位拦截，含被拦接口）、`retrieval_degraded`（语义→关键词）、`backend_offline_entered`、`capability_unavailable_shown` | **验证"边界可控"是否真被用户使用**：用户是否主动调档？降级是否被感知？后端离线是否被正确告知？ |
| 交付 | `report_export_started`、`report_export_completed`、`report_export_failed`（带格式与错误类别） | 报告导出成功率与格式偏好 |
| 调度 | `schedule_created`、`schedule_triggered`、`schedule_failed`、`schedule_paused` | 验证"真实调度"是否被使用 |
| 异常 | `error_occurred`（前端 + API + LLM 三类分开） | 错误分类分布 |

### 10.2 埋点实现要求

- **命名规范**：`{对象}_{动作}`（如 `dataset_created`、`llm_fallback_triggered`、`report_export_completed`）
- **公共属性**：每个事件附带 `user_id`（匿名 ID）、`timestamp`、`device`、`browser`、`app_version`、`request_id`
- **隐私红线**：**不上报 IP、不上报原始数据行、不上报用户输入的完整查询文本**（查询文本仅上报长度与是否含敏感关键词的布尔值）
- **实现方式**：前端轻量 `trackEvent()` 封装（统一出口，便于替换 SDK）+ 后端中间件自动记录 API 与 LLM 事件；不做全量自动埋点（避免事件爆炸）
- **可验证**：埋点事件必须在开发环境有调试面板可实时查看（否则埋点等于没埋）

### 10.3 MVP 核心验证问题（埋点是为了回答这四个问题）

1. **AI 可信链路真的缩短了"从数据到结论"的距离吗？** → 看 `ttfi_measured` 分布 + `text2sql_generated` 到 `analysis_completed` 的转化
2. **"可审计的 SQL"是被用户需要的吗？** → 看 `sql_manually_edited` 占比（若接近 0，说明用户信任生成结果；若偏高，说明透明度确实是刚需且生成质量待提升）
3. **记忆与知识库是否创造了复利？** → 看 `return_visit` 用户中 `memory_viewed` / `kb_retrieval_hit` 的比例，以及第 N 次会话相对第 1 次的追问轮数变化
4. **"可配置的隐私边界"是真需求还是自嗨？** → 看 `privacy_mode_changed` 占比（若长期为 0，说明默认档已够用，档位是过度设计；若有人主动上调到 `standard` / `full`，说明边界确实被不同用户群需要）

## 12. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| LLM 生成 SQL 准确率不足，单表也达不到 85% | 核心差异化卖点受损 | 用 50 条标注问题集在 F1 网关落地后立即建立基线；不达标则加强 schema 提示 + 少样本示例 + 规则兜底，不硬上线 |
